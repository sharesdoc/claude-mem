# 修好了"方法不存在"的问题后，省钱模型切换功能对主流程其实还是不起作用

## 1. 问题状态

- 问题等级：P1
- 完成状态：已关闭
- 测试状态：无需测试
- 概要描述（大白话）：`Issue-20260928164327221-P0-Tst.md` 修好了"分级路由查不到数据"这个方法调用错误，但本地在写回归测试验证这个修复时发现，实际生产代码把每一批"轮次切片"任务都打上了统一的固定标签（不管里面真实内容是什么），而分级路由判断"是不是简单任务""是不是总结任务"靠的正是这个标签。结果就是：方法调用的错误修好了，但因为标签本身从一开始就没法反映真实内容，分级路由对现在最主要的这套新流程来说，实际上还是永远选不中"简单模型"或"总结模型"，只是不再报错了而已，省钱效果基本没恢复。

- 所属计划项：无（项目无 M-系统开发计划体系）

## 2. 问题描述

**正常应该怎样**：分级路由（tier routing）看上一轮里的任务都是什么类型——全是简单只读工具（读文件、搜索之类）就换成便宜模型；全是要写总结的任务就换成专门配置的总结模型；混杂的就用默认模型。这个判断的依据是每条待处理任务记录的"消息类型"（`message_type`，是 `observation` 还是 `summarize`）和"工具名字"（`tool_name`，比如 `Read`、`Grep`）。

**实际怎样**：这批改动引入的"轮次切片"新流程里，一整轮对话产生的所有原始事件（可能是好几个工具调用、也可能混着总结请求），最终会被打包成一条或几条"切片"任务塞进队列。但打包这一步（`src/services/worker/SessionManager.ts` 的 `flushInputRound` 方法，第 387-389 行）不管这一批事件里实际是什么内容，永远把这条任务的类型写死成：
```ts
type: 'observation',
tool_name: 'input_round_slice',
```
`'input_round_slice'` 只是一个占位符名字，不是真实工具名，也不在分级路由认识的"简单工具白名单"（`Read`/`Glob`/`Grep`/`LS`/`ListMcpResourcesTool`）里。

更进一步，即使有代码想在打包时如实标注"这批里有总结任务"（比如传 `type: 'summarize'`），`src/services/sqlite/PendingMessageStore.ts` 第 92 行的 SQL 语句里，`message_type` 这一列的值在 SQL 语句里被写死成了字面量 `'observation'`，不管调用方传的 `message.type` 到底是什么——这是比 `flushInputRound` 更底层的一道"关卡"，任何调用方都绕不过去。

所以最终结果是：只要一条待处理任务是"轮次切片"，它在数据库里的 `message_type` 永远是 `observation`，`tool_name` 永远是 `input_round_slice`。分级路由的两条判断规则：
- "是不是全是总结任务"（`message_type === 'summarize'`）——永远不成立；
- "是不是全是简单工具"（`tool_name` 在白名单里）——因为 `tool_name` 永远是 `input_round_slice`，不在白名单里，也永远不成立。

两条规则都不成立时，分级路由的代码逻辑会保留默认模型，不做任何切换。

**触发条件**：只要一次会话的某一轮被"轮次切片"机制处理过（这是这批改动引入后的标准/主要处理路径，不是边缘情况），下一轮的分级路由判断就必然落空，只能用默认模型。

**复现方法**：
1. 完成 `Issue-20260928164327221-P0-Tst.md` 的修复（分级路由能正常查到轮次切片数据）。
2. 配置好分级路由：`CLAUDE_MEM_TIER_ROUTING_ENABLED=true`、`CLAUDE_MEM_TIER_SIMPLE_MODEL`、`CLAUDE_MEM_TIER_SUMMARY_MODEL` 都填好。
3. 让某一轮对话的内容经过 `flushInputRound` 打包成轮次切片（这是每轮对话结束时的标准处理路径）。
4. 下一轮触发生成器启动时观察实际使用的模型——即使这一轮全是简单的读文件操作，实际用的也不会是配置的便宜模型，而是默认模型。

**复现路径**：
- `src/services/worker/SessionManager.ts:387-389`（`flushInputRound` 硬编码 `type`/`tool_name`）
- `src/services/sqlite/PendingMessageStore.ts:92`（`enqueueRoundSlice` 的 SQL 语句硬编码 `message_type` 为 `'observation'` 字面量）
- `src/services/worker/http/routes/SessionRoutes.ts` 里 `applyTierRouting` 的 `hasSummarize`/`allSimple` 判断逻辑（依赖上述两个字段）
- 本地新增测试 `tests/services/worker/http/routes/session-routes-tier-routing.test.ts` 里 `'coerces round-slice message_type to observation at the storage layer...'` 这条用例，直接实测验证了这个现象

**影响范围**：分级路由这个"省钱"功能本身还配置着、界面上看起来也没报错，但对这批改动引入的主流程（轮次切片）来说，实际上从一开始就没有真正发挥过作用——所有走这条主流程的对话轮次都用不上便宜模型或总结模型。范围是所有开启了分级路由、且使用了轮次切片机制的用户（现在这已经是标准处理路径），不是极端场景。不是数据损坏或安全问题，用户能正常使用产品，只是省钱功能名存实亡；同时这也说明 `Issue-20260928164327221-P0-Tst.md` 的修复价值主要在于"让代码变得诚实、可编译期发现类似错误"，而不是"恢复了省钱效果"——两者需要分开看待，因此单独定级 P1（而非跟随前一份定 P0）：既不是数据/安全类问题，也有一个诚实的默认模型兜底（不会用错模型、不会报错），只是没有拿到预期的成本优化效果。

## 3. 根因分析

**分析方法**：代码走查（沿"轮次切片生成 → 存储 → 分级路由读取判断"的数据流追踪）+ 假设-验证（写回归测试直接实测确认假设）。

**分析过程**：

1. 在给 `Issue-20260928164327221-P0-Tst.md` 写"轮次切片里全是总结任务 → 应该选中总结模型"的回归测试时，测试断言失败，实际结果是默认模型，不是预期的总结模型。
2. 排查测试断言失败的原因：查询测试用的内存数据库，发现 round slice 记录的 `message_type` 列的值是 `observation`，不是测试代码传入的 `summarize`。
3. 定位到 `PendingMessageStore.ts` 第 92 行的 SQL 语句，确认 `message_type` 在 `VALUES` 子句里是字面量 `'observation'`，不是参数占位符——这是 SQL 层面的硬编码，不受调用方传参影响。
4. 进一步确认 `flushInputRound`（生产代码里唯一真正生成轮次切片任务的地方）本身在调用入队之前，就已经把 `type` 和 `tool_name` 写死成固定值，即使 `PendingMessageStore.ts` 的硬编码被修掉，`flushInputRound` 这一层依然会让 `tool_name` 恒为 `input_round_slice`，分级路由的"简单工具白名单"判断依然不会命中。
5. 写了一条独立测试直接验证"通过正常入队接口传入 `type: 'summarize'` 的轮次切片，实际存进数据库的 `message_type` 是什么"，实测确认是 `observation`，证实这不是猜测，是可复现的确定性行为。

**关键证据**：
- `src/services/worker/SessionManager.ts:387-389`
- `src/services/sqlite/PendingMessageStore.ts:85-93`（`enqueueRoundSlice` 完整 SQL 语句）
- `tests/services/worker/http/routes/session-routes-tier-routing.test.ts` 里新增的对照测试（`'coerces round-slice message_type to observation at the storage layer...'`）
- 同一测试文件里 BullMQ 引擎那一侧的对照测试：BullMQ 的存储实现（`job.data` 直接保留调用方传入的对象）没有这道硬编码，所以同样的输入在 BullMQ 引擎下确实能得到 `summary-model`——这也顺带暴露了 SQLite 引擎和 BullMQ 引擎在"轮次切片的 message_type 该不该保真"这件事上行为不一致，是本问题的一个附带发现

**根本原因**：这批改动设计"轮次切片"机制时，只考虑了"把一整轮的原始事件打包成一份待处理任务，交给模型统一处理"这个主线需求，没有同步考虑"分级路由需要靠 `message_type`/`tool_name` 判断任务的简单/复杂程度"这条既有规则该怎么和新的批处理粒度对接——批处理之后，一条任务不再对应"一个工具调用"，而是对应"一整批可能混杂的事件"，用单一的 `message_type`/`tool_name` 字段已经没法准确描述"这一批里到底是什么内容"，所以设计时干脆用了固定占位符，但没有意识到、也没有同步更新分级路由那边依赖这两个字段做判断的逻辑，导致两个机制在这批改动里"接不上"。

**未解开的疑点**：
- 轮次切片打包时，是否应该、以及能不能合理地推导出"这批事件的分级路由分类"（比如批内事件的工具名全部为白名单简单工具时才标记为"简单"，否则标记为"混合"）？这涉及到对"批处理"和"分级路由"两个机制的重新设计，需要产品/架构层面拍板，不是本档案能单方面下结论的技术细节。
- `PendingMessageStore.ts` 硬编码 `message_type` 为 `'observation'`，是否还有除分级路由外的其他消费方依赖"轮次切片的 message_type 一定是 observation"这个约定（比如某处代码专门判断 `message_type === 'observation' && tool_name === 'input_round_slice'` 来识别"这是一条轮次切片"）？如果有，贸然改成保留真实类型可能会破坏那部分逻辑，需要在解决方案阶段先排查清楚。

## 4. 解决方案

**【结论先说】**：这不是一个能靠改一两行代码就治好的小毛病，而是"批处理"和"按单个任务类型做模型分级"这两个设计之间存在根本性的错位，需要重新设计"分级路由该怎么理解一批混合内容"，建议作为一个独立的设计任务来处理，不建议在这里仓促给出代码级方案。

**候选方向一：批内容感知分级（工作量较大）**
- **怎么做**：轮次切片打包时（`flushInputRound`），不再用固定的 `type`/`tool_name`，而是分析这一批原始事件的真实构成——如果全部是白名单里的简单工具调用，就标记为"简单批次"；如果里面有总结请求，标记为"总结批次"；否则标记为"混合批次"。分级路由据此判断，逻辑上和现在保持一致，只是判断依据从"单条任务的字段"变成"整批任务的构成分析"。
- **好处**：能真正恢复省钱效果，且和现有分级路由的设计理念保持一致。
- **代价与风险**：需要重新设计轮次切片的分类规则、可能需要新增字段或调整现有 `message_type`/`tool_name` 的语义，改动面较大，需要评估是否会影响其他依赖这两个字段现有约定的代码（见"未解开的疑点"）。
- **适用前提**：产品认为"分级路由的省钱效果"值得为此投入设计和开发成本。

**候选方向二：接受现状，只做诚实标注（工作量很小）**
- **怎么做**：不改变现有行为（轮次切片依然固定用默认模型），但在代码注释、设置项说明或用户文档里明确写清楚"分级路由目前不对轮次切片批次生效，只对未走批处理的场景生效"，避免用户误以为配置了分级路由就一定会省钱。
- **好处**：改动量最小，不引入新的复杂度或风险。
- **代价与风险**：没有真正解决省钱效果缺失的问题，只是让预期更准确；如果分级路由本身对用户来说很重要（比如是主要的成本控制手段），这个方向可能不够。
- **适用前提**：如果轮次切片带来的批处理效率收益本身已经足够抵消"分级路由暂时用不上"的成本，或者分级路由本来就是可有可无的优化项，可以先用这个方向过渡。

**最优解与理由**：本档案不代为拍板选哪个方向——这需要产品/架构层面权衡"分级路由省下的模型成本"和"重新设计批处理分级机制的开发成本"哪个更划算，超出了单纯"修 bug"的范畴。建议先按候选方向二做一次诚实标注（成本很低、立即可做），把候选方向一作为后续的独立设计任务排期。

**实施步骤**（候选方向二，可立即执行的最小动作）：
1. 在 `SessionManager.ts` 的 `flushInputRound` 方法附近补充注释，说明"轮次切片任务目前不参与分级路由的简单/总结分类，始终使用默认模型"。
2. 视需要在面向用户的分级路由配置说明（如果存在）里同步这一限制。

**回退办法**：候选方向二只是加注释，没有代码行为变化，无需回退考虑；候选方向一涉及具体设计后再评估。

## 5. 关联影响

- **横向影响**：分级路由的设置项（`CLAUDE_MEM_TIER_ROUTING_ENABLED`、`CLAUDE_MEM_TIER_SIMPLE_MODEL`、`CLAUDE_MEM_TIER_SUMMARY_MODEL`）本身的读取、校验逻辑不受影响，问题只出在"判断依据的数据从哪来"这一层。
- **纵向影响**：如果未来采纳候选方向一，会涉及 `pending_messages` 表的字段语义调整（`message_type`/`tool_name` 对轮次切片场景可能需要新的分类维度），需要评估现有依赖这两个字段的其他查询/逻辑（比如 `peekPendingTypes`/`peekPendingTypesForPrompt` 等其他查询方法）是否也需要跟着调整。
- **文档与注释**：如果分级路由对外有面向用户的说明文档，需要同步更新其适用范围。
- **同类隐患**：`PendingMessageStore.ts` 里"SQL 语句硬编码某个字段值"这种写法本身值得留意，建议排查是否还有其他地方存在类似的"入队参数被静默覆盖、和调用方预期不符"的情况——这属于举一反三的排查项，不在本档案范围内展开。
