# 用户标了"不要存"的私密内容，还是被永久明文存进了数据库

## 1. 问题状态

- 问题等级：P0
- 完成状态：已关闭
- 测试状态：测试通过
- 概要描述（大白话）：用户在输入里用 `<private>` 标签整个包住的内容，或者一句话跟之前发过的重复了，本来应该被当成"不存档"处理，但代码里存档那一步偷偷用了没脱敏的原始文字，结果这些用户主动标记为私密的内容，被原样永久写进了一张连删都删不掉的数据库表里。
- 分析依据 / 来源：本次代码审查（审查范围 commit `dd51045a3a5864e902eb4f79506dc84759a40670`(不含) 到 `5138a6b742d18e42479d8c2ff9fd18290d83ece0`(含)，7 个提交、51 个文件），本地独立发现并核实，未在远端（ChatGPT）审查报告中出现。
- 所属计划项：无（项目无 M-系统开发计划体系）

## 2. 问题描述

**正常应该怎样**：用户在发给系统的话里用 `<private>...</private>` 包住不想被存档的内容，系统应该把这部分内容从要存的文字里去掉之后再存，或者整句话都是私密内容时干脆不存。这是项目自己写在 `CLAUDE.md` 里的承诺："`<private>content</private>` - User-level privacy control (manual, prevents storage)"（用户可以手动标记私密内容，效果是阻止存储），而且明确写着"Tag stripping happens at hook layer (edge processing) before data reaches worker/database"（标签清除发生在最前端的处理环节，数据到达数据库之前就已经清除）。

**实际怎样**：在两种情况下，代码把**没有清除标签、原汁原味的原始文字**存进了数据库，而不是清除过的文字：

1. **整句话都是私密内容**（清除标签后剩下空字符串）：`src/services/worker/http/routes/SessionRoutes.ts` 第 500-505 行：
   ```ts
   const cleanedPrompt = stripMemoryTagsFromPrompt(prompt);   // 500 行：清除后的干净文字
   if (!cleanedPrompt || cleanedPrompt.trim() === '') {
     this.sessionManager.recordUserInputEvent(sessionDbId, prompt, promptNumber, ...);  // 503 行：传的是没清除过的 prompt，不是 cleanedPrompt
   ```
2. **这句话和最近说过的话重复**（去重分支）：同文件第 521-530 行：
   ```ts
   const duplicatePrompt = store.findRecentDuplicateUserPrompt(contentSessionId, cleanedPrompt, ...);
   if (duplicatePrompt) {
     this.sessionManager.recordUserInputEvent(sessionDbId, prompt, duplicatePrompt.prompt_number, ...);  // 528 行：同样传的是 prompt，不是 cleanedPrompt
   ```

`recordUserInputEvent` 的实现在 `src/services/worker/SessionManager.ts`（`beginInputRound`/`recordUserInputEvent` 方法），会把传入的文字原样交给 `RawEventStore.append()`（`src/services/sqlite/RawEventStore.ts`）写进 `raw_events` 表的 `tool_input`/`payload` 字段——`RawEventStore.append()` 本身没有做任何脱敏处理，传什么就存什么（见 `RawEventStore.ts` 全文，`serialize()` 函数只是做 JSON 序列化，不做内容过滤）。

更严重的是，`raw_events` 表在设计上就是"删不掉"的：`schema.sql` 第 160-163 行的注释写着："raw_events: append-only archive of original hook payloads. It intentionally has no FK to sdk_sessions so session cleanup cannot erase it."（原始事件的只追加归档表，故意不关联会话表的外键，这样清理会话时也删不掉它）。也就是说，一旦私密内容被写进这张表，用户没有任何正常途径能把它删除。

**触发条件**：
- 用户发的一条消息整体被 `<private>...</private>` 包住（这是项目文档里明确介绍给用户的隐私功能，任何用户都可能正常使用）；
- 或者用户短时间内发了两条内容相同的消息（`USER_PROMPT_DEDUPE_WINDOW_MS` 时间窗口内的去重判断）。

**能否复现**：能。这是纯逻辑错误（变量传错了），只要具备触发条件必然发生，不依赖时序或并发，100% 复现。

**复现路径**：
1. 通过 hook 调用 `SessionRoutes` 的会话初始化接口（`handleSessionInitByClaudeId`，对应 HTTP 路由），传入一条完整用 `<private>敏感内容</private>` 包裹的 `prompt`。
2. 查询 SQLite 数据库 `~/.claude-mem/claude-mem.db` 的 `raw_events` 表，按 `content_session_id` 过滤，检查 `tool_input`/`payload` 字段是否包含未脱敏的 `敏感内容` 明文。

**影响范围**：所有使用 `<private>` 标签功能的用户、所有触发去重逻辑的用户。这是 claude-mem 插件面向所有安装用户的公开隐私功能，影响面是全体用户；后果是本该被保护的敏感信息被永久明文归档，且无法通过正常渠道删除——按项目的问题分级地板规则（涉及敏感信息泄露的问题不得低于 P1），加上"无绕过、用户正在正常使用隐私功能却被反向记录"，定为 P0。

## 3. 根因分析

**分析方法**：变更差分法（对比这批改动前后的代码差异，看谁引入了问题）+ 代码走查（沿数据流从写入点回溯到消费点）。

**分析过程**：

1. 先确认"清除标签"这个动作本身是正常工作的：`stripMemoryTagsFromPrompt(prompt)` 在第 500 行被调用，结果存进 `cleanedPrompt`，后续 552 行往下的正常入库分支（`store.saveUserPrompt(...)`）用的就是 `cleanedPrompt`，脱敏是生效的。
2. 但两个"提前返回"的分支（整体私密、命中去重）里，`recordUserInputEvent` 的第二个参数写的是 `prompt`（原始未脱敏变量），而不是本该用的 `cleanedPrompt`。
3. 用 `grep` 核实 `recordUserInputEvent` 的实现（`SessionManager.ts`）与底层存储（`RawEventStore.ts`）都没有二次脱敏的保护层，确认这是唯一一道脱敏关卡，一旦这里传错，后面没人兜底。
4. 用 `git diff dd51045a..5138a6b7 -- src/services/worker/http/routes/SessionRoutes.ts` 确认：`recordUserInputEvent` 这两处调用是本批新增的代码（配合 `raw_events`/`input_rounds` 归档功能一起加入），不是历史遗留问题——是这次"原始事件持久化"改动引入的新问题。

**关键证据**：
- `src/services/worker/http/routes/SessionRoutes.ts:500`（`cleanedPrompt` 定义）
- `src/services/worker/http/routes/SessionRoutes.ts:503`（错误调用 1，私密分支）
- `src/services/worker/http/routes/SessionRoutes.ts:528`（错误调用 2，去重分支）
- `src/services/worker/SessionManager.ts` 的 `recordUserInputEvent` 方法定义（原样转发给 `RawEventStore.append`）
- `src/services/sqlite/RawEventStore.ts` 全文（无脱敏逻辑）
- `src/services/sqlite/schema.sql:160-163`（`raw_events` 表设计注释，说明其"删不掉"的性质）
- 项目根 `CLAUDE.md` "Privacy Tags" 一节（隐私承诺原文）

**根本原因**：这批改动新增了"把每一次用户输入都原样归档进 `raw_events`"的功能（为了支持"输入轮次批处理"新特性），但实现时在两个提前返回分支里，写代码的人直接复用了函数作用域里已经存在的原始变量 `prompt`，而不是刚刚算出来的、专门为了脱敏而存在的 `cleanedPrompt` 变量——本质是一处变量误用，但因为踩在隐私保护的关键路径上，后果被放大成了真实的数据泄露。

**未解开的疑点**：
- 是否所有历史已产生的 `raw_events` 记录里，已经存在被误存的私密内容？这需要在数据库里做一次实际排查（按 `event_type='user_input'` 过滤，人工或脚本抽查 `payload` 是否命中 `<private>` 标签片段），本档案不下结论，留给修复阶段处理。
- `beginInputRound`（正常入库路径）里传的是 `cleanedPrompt`（第 578 行附近），说明写这段代码的人清楚"该传脱敏后的版本"这个规则，只是在另外两个分支上漏掉了——不是不懂规则，是两处分支遗漏，这点已用代码比对确认，不是假设。

## 4. 解决方案

**【结论先说】**：把这两处传参从 `prompt` 改成 `cleanedPrompt` 就能修好，改动量极小（两行），没有任何架构上的风险，建议立刻改。

**推荐方案：直接改传参**
- **怎么做**：`SessionRoutes.ts` 第 503 行、第 528 行，把 `recordUserInputEvent(sessionDbId, prompt, ...)` 改成 `recordUserInputEvent(sessionDbId, cleanedPrompt, ...)`。
- **好处**：改动最小、语义清晰（"归档的应该是脱敏后的文字"这条规则和 `beginInputRound` 的既有用法保持一致）、不影响其他任何逻辑。
- **代价与风险**：几乎没有。唯一要注意的是，第 502 行分支里 `cleanedPrompt` 此时已经是空字符串（因为整句话都是私密内容），传空字符串给 `recordUserInputEvent` 在语义上是合理的（代表"这条输入的可归档内容为空"），不会引发异常——`RawEventStore.append` 对空字符串和 `null` 都能正常处理（`serialize()` 函数对字符串直接返回，不会报错）。
- **适用前提**：无特殊前提，直接适用。

**备选方案：从根源上不归档私密事件**
- **怎么做**：在 `cleanedPrompt` 为空的分支里，完全跳过 `recordUserInputEvent` 调用（不产生任何 `raw_events` 行），只在日志里记一条"跳过了一次私密输入"的脱敏后统计信息（比如只记长度，不记内容）。
- **好处**：更彻底地贯彻"private 内容不落库"的产品承诺，即使 `cleanedPrompt` 这类中间变量将来又被写错，也不会有内容泄露风险（因为压根不调用存储函数）。
- **代价与风险**：需要同时确认"完全不归档"是否会影响这次改动引入的"输入轮次批处理"功能对私密消息的边界处理逻辑（比如该轮次的 `input_rounds`/`round_slices` 计数是否依赖这条空记录）——需要在实施前额外确认关联影响（见第 5 段）。
- **适用前提**：如果团队认为"私密消息不该在 `raw_events` 留任何痕迹"（哪怕是空文本），选这个更彻底；如果只是想修复"传错变量"这个具体问题，选推荐方案即可。

**最优解与理由**：推荐**直接改传参**方案。这次问题的根本原因就是传错了一个变量，不是设计缺陷；改一行代码就能让行为符合项目自己写的隐私承诺，风险最低、见效最快。备选方案的"彻底不落库"目标更好，但涉及连带评估，可以作为后续加固项，不需要阻塞这次修复。

**实施步骤**：
1. 改 `src/services/worker/http/routes/SessionRoutes.ts` 第 503 行、第 528 行，`prompt` → `cleanedPrompt`。
2. 补一个单元测试：模拟一条整体被 `<private>` 包裹的 prompt，断言 `RawEventStore`/`raw_events` 里没有出现任何私密明文片段。
3. （可选，需用户确认后再做）写一个一次性排查脚本，扫描现有数据库里 `raw_events` 表 `event_type='user_input'` 的记录，看是否已有历史泄露数据，如有则由用户决定是否需要清理。

**回退办法**：这是两行字符串变量替换，如果改完后发现有意料之外的副作用，直接把 `cleanedPrompt` 改回 `prompt` 即可完全回退，无数据结构变更、无迁移脚本，回退零风险。

## 5. 关联影响

- **横向影响**：`recordUserInputEvent` 目前只在 `SessionRoutes.ts` 这两处被调用（已用 grep 核实），改动不会影响其他调用方。
- **纵向影响**：
  - `raw_events` 表的数据内容会变得更"干净"（不再包含未脱敏文字），不影响表结构、不需要数据库迁移。
  - 这次改动新增的"输入轮次批处理"功能（`InputRoundStore`/`round_slices`）依赖 `raw_events` 里的记录来切片处理，需要确认"私密分支不产生记录（备选方案）"或"私密分支产生空内容记录（推荐方案）"是否会影响轮次切片的计数逻辑——推荐方案因为仍然产生一条记录（只是内容变干净），对轮次逻辑没有影响，这也是推荐方案更稳妥的原因之一。
  - 若采纳"补排查脚本"的可选步骤，需要用户对现有生产数据库有访问权限并明确授权，属于数据层面的敏感操作，不能擅自执行。
- **文档与注释**：不需要改文档，`CLAUDE.md` 里的隐私承诺描述本身是对的，是代码没有兑现承诺，不是文档需要更新。
- **同类隐患**：需要检查项目里其他"提前返回/跳过正常流程"的分支，是否也存在"该用脱敏变量却用了原始变量"的同类模式——这属于举一反三的排查项，建议后续单独扫一遍，不在本档案范围内展开。

## 6. 回归测试

**验证目标**：证明整体私密输入和重复输入这两种场景下，`raw_events` 表里不会再出现未脱敏的原始文字。

**测试方法**：单元测试 + 手工验证。

**测试步骤**：
1. 单元测试：构造一条 `prompt = "<private>敏感数据ABC123</private>"`，调用会话初始化的处理逻辑（或直接调用 `recordUserInputEvent` 所在的调用路径），断言写入 `raw_events` 的记录里，`tool_input`/`payload` 字段不包含 `敏感数据ABC123` 字样。
2. 单元测试：构造两条内容相同的 `prompt`（触发去重分支），同样断言归档记录里不包含未脱敏内容（如果原始内容本身不含 `<private>`，则这条测试主要验证"确实传的是 cleanedPrompt 变量"这个事实，可以通过临时让 `stripMemoryTagsFromPrompt` 对测试输入做一个可观察的转换来验证）。
3. 手工验证（可选）：起一个本地 worker，实际发一条私密消息，查 SQLite 数据库确认。

**通过判据**：上述两个单元测试均通过，且手工验证未在数据库里发现未脱敏明文，即为通过；只要有一处仍能查到未脱敏内容，即为不通过。
