# 让所有 AI 模型的名字都必须由用户自己填，程序不再偷偷用出厂默认值

## 1. 任务状态

- 任务等级：P2
- 完成状态：已关闭
- 测试状态：测试通过
- 概要描述（大白话）：现在 claude-mem 用来生成"记忆摘要"的这几家 AI（Claude、Qwen、DeepSeek、OpenRouter、Gemini），如果用户没有明确填写要用哪个具体型号（比如 `qwen3-max`），程序会自己偷偷补一个默认型号继续跑。这次要把这个"偷偷补默认值"的行为全部去掉：没显式配置型号名，次级几家（Qwen/DeepSeek/OpenRouter/Gemini）就当这家没法用、自动换下一家；轮到 Claude（最后一道兜底，没有更下一家可换）时，就直接报错提示用户去配置，不再悄悄垫一个默认型号。
- 来源与依据：用户在对话中明确提出（"如果 CLAUDE_MEM_QWEN_MODEL 没有被用户设置，则不启用模型，不能默认使用 qwen3-max"），并经两轮澄清问答确认扩大到全部 provider（含 Claude）、且确认方式为"次级厂商静默不可用回落链条／Claude 报错阻塞"。
- 所属计划项：无（独立 fix）
- 关联需求：N/A（项目仅有 A/B 两份逆向文档，未覆盖此运维配置类行为，本任务不改 A/B）

## 2. 需求描述

本任务要做的事，是把"模型名（型号）未显式配置时该怎么办"这件事，从"程序自己偷偷选一个能用的型号"改成"必须用户自己说清楚要用哪个型号，说不清楚就不让这条路生效"。范围覆盖两条独立运行时——插件日常使用的 worker 主路径（`src/services/worker/` 下的 QwenProvider / DeepSeekProvider / OpenRouterProvider / GeminiProvider / ClaudeProvider）和多租户场景下的 server-beta 独立路径（`src/server/generation/providers/` 下的 Claude / OpenRouter / Gemini 三个 ObservationProvider）。不做的事：不改 API Key（凭证）的解析逻辑，那条链路已经是"必须显式配置、缺失即报错/判不可用"，本次不涉及；不改 `provider-selection.ts` 里"先选中哪家厂商"的判定逻辑本身，只改各厂商自己对"我是否可用"的判断依据；不涉及前端页面或用户交互，纯后端配置解析行为调整。

使用场景是：用户设置了 `CLAUDE_MEM_PROVIDER=qwen` 并配了 `CLAUDE_MEM_QWEN_API_KEY`，但忘了填 `CLAUDE_MEM_QWEN_MODEL`——现状是程序会悄悄用 `qwen3-max` 顶上，用户可能完全不知道自己实际在用哪个型号跑记忆摘要；改完之后，Qwen 这条路会被判定为"不可用"，自动换到下一个候选厂商，最终换到 Claude；而如果用户什么 provider 都没配（这是插件"零配置默认可用"的最常见场景），走到 Claude 这一步、发现 `CLAUDE_MEM_MODEL` 也是空的，就会直接抛出一个说明清楚的报错，而不是像现在这样自动垫 `claude-haiku-4-5-20251001` 继续跑。

## 3. 需求分析

表面上这只是删掉几个 `|| DEFAULT_MODEL` 兜底表达式，但调查发现真正生效的默认值大多不在这几个表达式里，而是藏在 `src/shared/SettingsDefaultsManager.ts` 的 `DEFAULTS` 常量对象里：`CLAUDE_MEM_MODEL`、`CLAUDE_MEM_GEMINI_MODEL`、`CLAUDE_MEM_OPENROUTER_MODEL`、`CLAUDE_MEM_DEEPSEEK_MODEL` 这四个字段在 `DEFAULTS` 里本来就写死了非空的出厂型号名（只有 `CLAUDE_MEM_QWEN_MODEL` 出厂就是空串）；`loadFromFile()` 在合并用户配置时，用户没填的字段会直接落回 `DEFAULTS` 里的这个非空值，也就是说各 provider 文件里 `resolveXModel()` 函数拿到的 `settings.CLAUDE_MEM_XXX_MODEL` 参数，在运行时几乎永远不是空字符串——单改这几个 `resolveXModel()`/`getXConfig()` 函数本身，实际运行路径根本不会触发"空则怎么办"这个分支，改动等于摆设。因此本任务的真正落点必须同时包含 `SettingsDefaultsManager.ts` 里这四个字段的出厂值。

四个次级厂商（Qwen/DeepSeek/OpenRouter/Gemini）在 `provider-selection.ts` 的选型链条上都是"可选可跳过"的角色——`resolveProviderId()` 只有在 `isXSelected() && isXAvailable()` 同时为真时才启用某家，任一为假就自动尝试下一家，最终无条件落到 `claude`。这意味着让这四家的 `isXAvailable()` 多加一条"模型名也必须非空"的判断，天然就能复用现有的"选型跳过"机制，不需要改 `provider-selection.ts` 本身。而 Claude 是这条链条的终点、`resolveProviderId()` 对它没有任何可用性前置判断（无条件兜底），所以模型名缺失时没有"跳到下一家"这个选项可用，只能在 `ClaudeProvider.startSession()` 内部直接抛错阻塞——这与 server-beta 路径下三个 ObservationProvider 构造函数已有的"API Key 缺失即抛 `ClassifiedProviderError`"先例风格一致，可以直接照着抄一份"模型名缺失即抛错"的校验。

假设/待确认：本任务把这次改动的影响范围认定为"运维配置类变更"，不属于 A/B 文档描述的业务需求范畴，所以不标记"需 ree 刷新"；如果后续认为这类 AI 供应商配置行为也应该写进设计文档，需要用户另行决定是否委托 ree 补充。

## 4. 设计方案

【最优解】按"厂商在选型链条中的位置"分两套动作，改动只落在配置解析与可用性判断这一层，不动选型链条主逻辑本身，理由是这样改动面最小、且完全复用现有的"选型自动跳过"机制，不需要新发明一套降级逻辑：

**A. 出厂默认值清零**（`src/shared/SettingsDefaultsManager.ts`）：把 `DEFAULTS` 里 `CLAUDE_MEM_MODEL`、`CLAUDE_MEM_GEMINI_MODEL`、`CLAUDE_MEM_OPENROUTER_MODEL`、`CLAUDE_MEM_DEEPSEEK_MODEL` 四个字段的出厂值改成空字符串 `''`（`CLAUDE_MEM_QWEN_MODEL` 已经是空串，不用改）。这一步是让后面所有"判断模型名是否为空"的逻辑真正有意义的前提。

**B. 次级厂商——不可用则静默跳过**（`QwenProvider.ts` / `DeepSeekProvider.ts` / `OpenRouterProvider.ts` / `GeminiProvider.ts`，均在 `src/services/worker/`）：
- 各自的模型解析函数（`resolveQwenModel()` / DeepSeek 对应函数 / `getOpenRouterConfig()` 里的 model 那一行 / `getGeminiConfig()` 里的 `configuredModel`）去掉 `|| DEFAULT_MODEL`（或等价的 `defaultModel` 兜底）这一段，未配置时如实返回空字符串；未再被其他地方引用的 `DEFAULT_MODEL` 常量一并清理，避免留下死代码。
- 各自的 `isXAvailable()` 函数，在原有的"apiKey 是否存在"判断基础上，加一条"模型名是否非空"，两者都满足才算 available；两个条件的检查方式要贴合各厂商现有代码风格（Qwen/DeepSeek 走三级凭证解析同款风格，OpenRouter/Gemini 走 settings 直读风格），不统一抽成新的公共函数，避免超出本任务范围的重构。
- 各自的 `startSession()` 里，仿照 Qwen 现成的 `if (!apiKey) throw new Error(...)` 这种防御性前置校验风格，补一条"模型名为空也 throw"的校验——这是双重保险：即便 `isXAvailable()` 的选型判断在某种路径下被绕过，`startSession()` 自己也不会带着空模型名去发请求换回一个让人费解的上游报错。

**C. Claude——链条终点，缺失即报错阻塞**（`ClaudeProvider.ts`，worker 主路径）：`startSession()` 里 `const modelId = session.modelOverride || this.getModelId();` 这一行之后，补一条判断——`modelId` 为空（且没有走 `session.modelOverride` 这条显式覆盖路径）就直接 `throw new Error('Claude model not configured. Set CLAUDE_MEM_MODEL in settings or environment.')`，不再让请求带着空模型名继续往下走。

**D. server-beta 独立路径三个 ObservationProvider**（`src/server/generation/providers/` 下的 `ClaudeObservationProvider.ts` / `OpenRouterObservationProvider.ts` / `GeminiObservationProvider.ts`）：构造函数里 `options.model ?? DEFAULT_MODEL` 这种兜底去掉，模型名缺失时仿照这三个文件里已有的"API Key 缺失即抛 `ClassifiedProviderError`"先例风格，抛一个语义对应的"模型未配置"错误。由于调用方 `create-server-beta-service.ts` 目前是"模型名为空就不传 `model` 字段、交给构造函数默认值兜底"，改完构造函数后这条调用路径不需要额外改动——不传 `model` 字段会让构造函数里的新校验自然触发。

备选方案（未采用）：曾考虑把"模型名缺失"也归到 API Key 校验那一层统一处理（合并成一个"配置校验"函数），但这样会把四个厂商原本各自独立、风格不同的校验硬凑成一个新抽象，超出"只删默认值回落逻辑、补显式校验"的最小化改动范围，故不采用。

## 5. 关联影响

横向影响：`provider-selection.ts` 的 `resolveProviderId()`/`collectProviderFlags()` 不需要改代码，但其运行时行为会因为下游 `isXAvailable()` 判断条件变严而改变——原本"apiKey 配了就算这家可用"，现在会变成"apiKey 配了、模型名没配，一样判不可用"，这是本任务的核心意图，不是意外副作用。`tests/services/worker/provider-selection.test.ts` 现有测试是直接构造 flags 对象喂给纯函数，不依赖具体 provider 的 `isXAvailable()` 实现，预期不受影响，但仍需在验证阶段跑一遍确认。

纵向影响：`src/server/runtime/create-server-beta-service.ts` 里 claude/openrouter/gemini 三个分支目前都是"模型名为空就不传 `model` 字段"的写法，依赖下游构造函数的默认值兜底——这正是本任务改动会触达、且不需要额外改动调用方代码就能生效的下游点，需要在验证阶段确认这三条分支在模型名缺失时确实会抛出新错误而不是静默用回默认值。已生成记忆的历史数据（SQLite/Chroma 里的旧 observation/summary）不受影响，检索路径不经过任何 provider 的模型解析逻辑。

对"零配置直接跑 Claude"这条现有默认使用路径的影响：**预期会被破坏，且是本任务明确要达成的效果**——完成本任务后，一个从未设置过任何 `CLAUDE_MEM_*` 环境变量或 `settings.json` 的全新安装，Claude worker 路径会在 `getModelId()` 拿到空字符串后直接抛错，插件将无法在零配置状态下生成新的观察记录/摘要，必须用户显式设置 `CLAUDE_MEM_MODEL` 才能恢复正常。这一后果已经过用户两轮确认，非本任务实施过程中的意外发现。

需要同步的文档/配置：无 A-F 完整体系、无 `G-系统接口清单`，本任务不涉及接口契约联动（§3.5 不适用）；README 或用户可见的配置说明文档如果存在类似"CLAUDE_MEM_MODEL 有默认值 xxx"的措辞，建议使用者自行核对一遍（不在本任务自动处理范围内，本任务只改代码行为）。

## 6. 测试方案

验收标准：①`SettingsDefaultsManager` 的 `DEFAULTS` 里四个模型字段（`CLAUDE_MEM_MODEL`/`CLAUDE_MEM_GEMINI_MODEL`/`CLAUDE_MEM_OPENROUTER_MODEL`/`CLAUDE_MEM_DEEPSEEK_MODEL`）出厂值为空字符串；②Qwen/DeepSeek/OpenRouter/Gemini 四家在 apiKey 已配、模型名未配时，`isXAvailable()` 返回 `false`；模型名也配了则返回 `true`（不改变现状）；③四家的模型解析函数在模型名未配时返回空字符串，不再返回任何内置默认型号名；④四家的 `startSession()` 在模型名为空时直接抛出说明清楚的 `Error`；⑤`ClaudeProvider.startSession()` 在 `session.modelOverride` 未设置且 `getModelId()` 为空时抛出说明清楚的 `Error`，设置了 `modelOverride` 则不受影响正常运行；⑥server-beta 三个 ObservationProvider 构造函数在 `options.model` 未传且无法回落默认值时抛出对应的 `ClassifiedProviderError`（或该文件既有的等价错误类型）；⑦`provider-selection.ts` 现有测试全部保持通过，验证"跳到下一家"的链条行为未被破坏。

测试方法：项目测试框架是 `bun:test`（`package.json` 的 `test` 脚本为 `bun test`），已有 `tests/services/worker/provider-selection.test.ts` 可参照写法；本次涉及的 `QwenProvider`/`DeepSeekProvider`/`OpenRouterProvider`/`GeminiProvider`/`ClaudeProvider`/`SettingsDefaultsManager`/`ClaudeObservationProvider` 目前均无独立测试文件,需要新建（对纯函数——`resolveXModel`、`isXAvailable`、`DEFAULTS` 取值——直接单元测试；对涉及 `throw` 的 `startSession()`/构造函数路径，测试到"确实抛出预期错误"这一步即可，不需要真的打外部 API）。回归范围：跑 `bun test` 全量、`tsc --noEmit` 类型检查（`package.json` 无 lint 脚本，不适用）。建议测试层级：单元测试为主，不涉及前端、不需要端到端测试。
