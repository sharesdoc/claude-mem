# 用户标了"不要存"的私密内容，还没脱敏就先进了会话主表，甚至可能被发给大模型

## 1. 问题状态

- 问题等级：P0
- 完成状态：待处理
- 测试状态：未测试
- 概要描述（大白话）：用户发起一次新会话时，系统在还没来得及"清除私密标签"之前，就已经把整段原始文字（包括 `<private>` 标签包住的内容）存进了会话主表的一个字段里。这个字段不是无关紧要的日志，它后续会被读出来，拼进发给大模型（比如 Claude）的请求内容里——也就是说，用户标记为"不要存"的内容，不仅先被存了一份，还有实际路径会被真的发给第三方大模型服务。
- 分析依据 / 来源：这是在修复 `doc/Issue-20260928164327193-P0-Tst.md`（`raw_events` 表隐私泄漏问题）的过程中，由委托的远端（ChatGPT）在核实那份档案的推荐方案时独立发现的边界问题，本地已复核确认属实，独立建档跟踪，不与前一份档案合并（两者的存储位置、触发路径、下游风险都不同，是两个独立的标准问题）。
- 所属计划项：无（项目无 M-系统开发计划体系）

## 2. 问题描述

**正常应该怎样**：和 `Issue-20260928164327193-P0-Tst.md` 里说的一样，`<private>` 标签包住的内容，应该在任何会被持久化或者被发送出去的地方，都先被清除掉。

**实际怎样**：`src/services/worker/http/routes/SessionRoutes.ts` 的 `handleSessionInitByClaudeId` 方法里，代码执行顺序是这样的：

1. 第 482 行：`const sessionDbId = store.createSDKSession(contentSessionId, project, prompt, customTitle, platformSource);` —— 这一步用的是**原始、未清除标签的** `prompt` 变量。
2. 第 500 行才执行：`const cleanedPrompt = stripMemoryTagsFromPrompt(prompt);` —— 清除标签这一步，发生在第 1 步**之后**。

也就是说，"存会话记录"这个动作，比"清除私密标签"这个动作**先发生**，导致原始未脱敏的文字被传给了 `createSDKSession`。

再看 `createSDKSession` 内部（`src/services/sqlite/SessionStore.ts` 第 2305 行起）：会话第一次创建时，`userPrompt` 参数会被直接写入 `sdk_sessions.user_prompt` 字段；如果会话已存在（比如同一个会话又发了一次请求），且该字段之前是空的，也会被这次传入的值回填进去。不管走哪条分支，只要传入的是未脱敏文字，未脱敏文字就会进到这个字段里。

更值得关注的是这个字段后续会被怎么用：`src/services/worker/SessionManager.ts` 的 `initializeSession` 方法（第 130-168 行），在**没有拿到新的 `currentUserPrompt`** 的情况下，会用 `dbSession.user_prompt`（也就是刚才被污染的那个字段）作为这次会话对象的 `userPrompt` 值（第 146 行：`const userPrompt = currentUserPrompt || dbSession.user_prompt;`）。而 `SessionManager` 里有些调用 `initializeSession` 的地方确实没有传 `currentUserPrompt`（比如 `recordUserInputEvent`、`flushInputRound` 内部："`this.sessions.get(sessionDbId) ?? this.initializeSession(sessionDbId)`"，完全没传第二个参数）。

而这个会话对象的 `userPrompt` 字段，最终会被 `src/services/worker/ClaudeProvider.ts` 第 445-446 行读取，拼进发给大模型的初始化/续接提示词里：
```ts
? buildInitPrompt(session.project, session.contentSessionId, session.userPrompt, mode)
: buildContinuationPrompt(session.userPrompt, session.lastPromptNumber, session.contentSessionId, mode);
```

**触发条件**：一次全新会话的第一条消息，如果整体被 `<private>` 标签包裹（这正是 `Issue-20260928164327193-P0-Tst.md` 里讨论的同一种用户操作），会话主表里就会先存进未脱敏文字；如果这次会话后续因为某些内部流程（比如工具调用产生的观察事件）先一步在没有传入新鲜 `userPrompt` 的情况下初始化了会话对象，这个会话对象缓存的 `userPrompt` 就会是未脱敏的版本，一旦这个会话后来触发生成器处理（发消息给大模型），就有被读取发送出去的风险。

**复现方法**（本地静态代码核实，尚未做端到端实测，见第 6 段）：
1. 发起一次全新会话，第一条消息整体是 `<private>敏感内容</private>`。
2. 查询数据库 `sdk_sessions` 表对应这个 `content_session_id` 的记录，检查 `user_prompt` 字段——预期应该是空/脱敏后的文字，实际会看到原始的 `<private>敏感内容</private>` 全文。
3. （需要进一步端到端验证）构造一个场景，让 `recordUserInputEvent` 在 `session.userPrompt` 被正常流程刷新之前，先被调用一次去初始化 `ActiveSession`，然后触发生成器启动，观察实际发给大模型的请求内容里是否包含未脱敏文字。

**影响范围**：所有第一条消息就用 `<private>` 标签的新会话，都会触发"未脱敏文字进入 `sdk_sessions.user_prompt`"这一步（这部分是本地已用代码核实、高置信度的事实）。是否会进一步被实际发送给大模型，取决于会话对象初始化的具体时序（这部分本地只核实到"代码路径上存在这种可能性"，尚未做端到端复现，属于本档案的待验证项，但基于地板规则——涉及敏感信息泄露的问题不得低于 P1，且这条路径比 `raw_events` 那份档案的风险更高（`raw_events` 只是"存起来"，这里是"可能被真的发给外部大模型服务"）——定为 P0。

## 3. 根因分析

**分析方法**：代码走查（沿"存储 → 读取 → 使用"的数据流追踪）+ 变更差分法（确认相关代码是否属于本批改动）。

**分析过程**：

1. 确认 `SessionRoutes.ts` 里 `createSDKSession` 调用（第 482 行）和 `stripMemoryTagsFromPrompt` 调用（第 500 行）的先后顺序：前者在前，后者在后，这是纯粹的执行顺序问题，用 `Read` 工具直接读源码行号确认，不是推测。
2. 确认 `SessionStore.createSDKSession`（`src/services/sqlite/SessionStore.ts:2305`）对 `userPrompt` 参数的处理：新建会话直接写入，已存在会话在字段为空时回填，两种情况都会把传入值原样存进 `sdk_sessions.user_prompt`。这部分逻辑是老代码（不是本批改动新增的），本批改动新增的是"`createSDKSession` 调用点传入的到底是脱敏前还是脱敏后的文字"这个上下文——本批新加的 `<private>` 相关代码路径（`recordUserInputEvent`/`raw_events` 归档）让这个已存在的老问题第一次有了明确的、可验证的隐私影响面。
3. 追踪 `sdk_sessions.user_prompt` 的读取方：`SessionManager.initializeSession`（第 146 行）在缺少新鲜 `currentUserPrompt` 时会回退读取这个字段。
4. 追踪 `session.userPrompt` 最终的消费方：`ClaudeProvider.ts` 第 445-446 行，确认它被直接拼进 `buildInitPrompt`/`buildContinuationPrompt`，这两个函数的返回值就是发给大模型的提示词内容（未展开验证 `buildInitPrompt`/`buildContinuationPrompt` 内部实现细节，但函数命名和调用位置已经足以说明这是"构造发给模型的提示词"这一步，如果这两个函数内部还有额外的脱敏步骤，会削弱本问题的风险，这一点是本档案的待验证项，见"未解开的疑点"）。

**关键证据**：
- `src/services/worker/http/routes/SessionRoutes.ts:482`（`createSDKSession` 调用，早于脱敏）
- `src/services/worker/http/routes/SessionRoutes.ts:500`（`stripMemoryTagsFromPrompt` 调用，晚于第 482 行）
- `src/services/sqlite/SessionStore.ts:2305-2334`（`createSDKSession` 对 `user_prompt` 字段的写入/回填逻辑）
- `src/services/worker/SessionManager.ts:146`（`initializeSession` 在缺少新鲜 prompt 时回退读取 `dbSession.user_prompt`）
- `src/services/worker/SessionManager.ts` 中 `recordUserInputEvent`/`flushInputRound` 内部调用 `initializeSession(sessionDbId)`（不传 `currentUserPrompt`）的写法
- `src/services/worker/ClaudeProvider.ts:445-446`（`session.userPrompt` 被拼进发给大模型的提示词构造函数）

**根本原因**：这次改动新增的"整体私密输入要脱敏后再处理"这条规则，只覆盖到了"归档到 `raw_events`"这一个存储点（即 `Issue-20260928164327193-P0-Tst.md` 修复的那两行），但同一个处理函数里更早执行的 `createSDKSession` 调用，从改动之前就一直在用未脱敏的 `prompt`——这次改动没有意识到"清除标签"这个动作需要**提到所有会存储/使用这份文字的调用之前**，而只是在归档这一个具体位置上做了局部处理。本质上和 `Issue-20260928164327193-P0-Tst.md` 是同一类错误（该用脱敏后的文字却用了原始文字），但发生在不同的代码位置、写入不同的表、有不同的下游消费路径（这个表的数据会被读出来拼进大模型请求），所以按"标准问题"的粒度铁律独立成档，不与前一份合并。

**未解开的疑点**：
- `buildInitPrompt`/`buildContinuationPrompt`（未在本轮定位到具体文件路径）内部是否有自己的一层脱敏处理？如果有，实际风险会降低（但即便如此，未脱敏文字进入 `sdk_sessions.user_prompt` 这件事本身依然是对"prevents storage"承诺的违反，只是"被发给大模型"这一步的风险可能被削弱）。这需要在修复阶段进一步查证 `buildInitPrompt`/`buildContinuationPrompt` 的具体实现。
- "会话对象在没有新鲜 `userPrompt` 的情况下被初始化，然后又触发了生成器"这个完整时序，本地只验证到"代码结构上存在这种调用方式"，还没有构造出一个完整的端到端测试去实际复现"未脱敏文字被发送给大模型"这个最终后果。这是本档案在"回归测试"阶段需要补齐的验证工作，目前的定级是按"地板规则+可信的代码路径证据"做出的，不是已经端到端实测确认的结论。

## 4. 解决方案

**【结论先说】**：把"清除标签"这一步提到最前面执行，让 `createSDKSession` 一开始拿到的就是已经脱敏过的文字，这样从源头上保证"未脱敏文字"根本不会进入 `sdk_sessions` 表，后面所有读取这个字段的地方自然也就安全了，不需要在每个读取点分别加防护。

**推荐方案：把脱敏动作提到 `createSDKSession` 调用之前**
- **怎么做**：调整 `handleSessionInitByClaudeId` 方法内部的执行顺序，把 `const cleanedPrompt = stripMemoryTagsFromPrompt(prompt);` 这一行移到 `store.createSDKSession(...)` 调用之前，然后 `createSDKSession` 的第三个参数改传 `cleanedPrompt`（而不是 `prompt`）。
- **好处**：一次改动堵住源头，不需要在 `SessionManager.initializeSession`、`ClaudeProvider` 等下游多个消费点分别加脱敏检查，符合"在数据进入系统的最早点清除标签"的既有设计原则（这也是项目 `CLAUDE.md` 里"Tag stripping happens at hook layer (edge processing) before data reaches worker/database"这句话真正应该落地的地方）。
- **代价与风险**：需要确认 `createSDKSession` 在"整体私密"场景下（`cleanedPrompt` 为空字符串）用空字符串创建/更新会话记录是否会引发其他逻辑问题——需要读 `createSDKSession` 内部对空字符串 `userPrompt` 的处理分支（第 2329 行 `if (userPrompt) { ... }`——空字符串是假值，会被这个判断跳过，回填逻辑不会执行，这属于安全的行为，但仍需要在实施时写测试明确验证）。
- **适用前提**：无特殊前提，是根治方案。

**备选方案：只在 `initializeSession` 读取 `dbSession.user_prompt` 时做一次防御性脱敏**
- **怎么做**：`SessionManager.initializeSession` 第 146 行附近，读取 `dbSession.user_prompt` 时再调用一次 `stripMemoryTagsFromPrompt`，作为兜底防护。
- **好处**：即使未来又有新的调用点不小心传入未脱敏文字给 `createSDKSession`，这一层兜底依然能拦住"发给大模型"这个最终风险。
- **代价与风险**：治标不治本——`sdk_sessions.user_prompt` 这个字段本身依然会存下未脱敏内容（只是读取时才清洗），没有解决"private 标签应该阻止存储"这个根本承诺；而且这个方法目前没有从数据库读到的路径专门做脱敏的先例，需要评估性能影响（虽然一次字符串处理的开销很小）。
- **适用前提**：可以作为推荐方案之外的**额外**加固层，两者不冲突，但不能替代推荐方案。

**最优解与理由**：推荐**把脱敏动作提到最前面**，同时建议把备选方案作为纵深防御一并加上（两者不冲突，属于"根治 + 兜底"的组合）。单独只做备选方案不能解决"数据被存进主表"这个问题本身。

**实施步骤**：
1. 调整 `SessionRoutes.ts` 第 480-505 行附近的执行顺序，`cleanedPrompt` 计算提前，`createSDKSession` 第三个参数改用 `cleanedPrompt`。
2. 追加读取 `buildInitPrompt`/`buildContinuationPrompt` 的具体实现，确认这两个函数内部有没有自己的脱敏逻辑，把这一点从"未解开的疑点"里去掉。
3. 视情况决定是否同时给 `SessionManager.initializeSession` 加防御性脱敏（备选方案）。
4. 补充端到端测试：验证"整体私密的新会话"场景下，`sdk_sessions.user_prompt` 字段不包含未脱敏文字；如果能够构造出触发生成器的完整场景，进一步验证发给大模型的请求内容里也不包含未脱敏文字。

**回退办法**：调整执行顺序是局部改动，可以直接用 git 恢复到改动前的代码，不涉及数据库结构变更，回退风险低。

## 5. 关联影响

- **横向影响**：`createSDKSession` 被多处调用（不只是 `handleSessionInitByClaudeId`，比如 `handleSummarizeByClaudeId` 里也有类似调用），需要排查是否有其他调用点也存在"传入未脱敏文字"的同类问题——这属于举一反三的排查项，本档案暂不展开，建议修复时一并核查。
- **纵向影响**：涉及 `sdk_sessions` 表现有数据（不是新表，是项目核心会话表），需要和 `Issue-20260928164327193-P0-Tst.md` 一样，评估是否要对历史数据做隐私影响排查（同样需要用户明确同意后才能操作生产数据库）；不涉及表结构变更。
- **文档与注释**：无需更新面向用户的文档，问题在于代码没有兑现文档承诺。
- **同类隐患**：和 `Issue-20260928164327193-P0-Tst.md` 属于同一根源类型的问题（脱敏时机不对/漏掉某个使用点），建议两份档案的修复一起验收，确认整个 `handleSessionInitByClaudeId` 方法里，凡是用到 `prompt` 原始变量的地方都已经过审查，没有第三个漏网的点。
