# 有个"是否保存原始记录"的开关，其实拨了也没用

## 1. 问题状态

- 问题等级：P2
- 完成状态：已关闭
- 测试状态：测试通过
- 概要描述（大白话）：这次改动新加了一个配置项，名字听起来像是"要不要保存原始事件记录"的开关，而且系统还专门写了校验规则说"这个值只能是开，不能关"。但实际上，无论这个配置项的值是什么，代码里所有真正写数据的地方压根就没去看这个配置项一眼，全都是无条件地写。也就是说，这是一个existing 但没人真正在用的"假开关"。因为正常的设置页面已经拦住了用户把它改成"关"这条路，所以普通用户目前碰不到这个问题，只是代码写得不严谨。
- 分析依据 / 来源：本次代码审查（审查范围 commit `dd51045a3a5864e902eb4f79506dc84759a40670`(不含) 到 `5138a6b742d18e42479d8c2ff9fd18290d83ece0`(含)，7 个提交、51 个文件）。此条最初由远端（ChatGPT）审查报告作为 P1-3 条目提出，本地核实后发现远端对"用户可触发路径"的判断有误，已修正场景描述并降级为 P2。
- 所属计划项：无（项目无 M-系统开发计划体系）

## 2. 问题描述

**正常应该怎样**：一个配置项如果存在，并且有专门的校验逻辑，通常意味着这个配置项是"真正会影响系统行为"的——要么它现在就能控制某个开关，要么至少校验逻辑和实际用途是一致的、不会互相矛盾。

**实际怎样**：
1. `src/shared/SettingsDefaultsManager.ts` 第 203 行新增了配置项 `CLAUDE_MEM_RAW_EVENT_STORE`，出厂默认值是字符串 `'true'`。
2. `src/services/worker/http/routes/SettingsRoutes.ts` 第 276-278 行有一段校验逻辑：
   ```ts
   if (settings.CLAUDE_MEM_RAW_EVENT_STORE !== undefined &&
       settings.CLAUDE_MEM_RAW_EVENT_STORE !== 'true') {
     return { valid: false, error: 'CLAUDE_MEM_RAW_EVENT_STORE must remain "true" because raw events are always retained' };
   }
   ```
   翻译成人话：如果用户想通过设置页面/设置接口把这个值改成 `'true'` 以外的任何值，请求会被直接拒绝，报错信息也明确写着"因为原始事件总是会被保留"。
3. 但是，用 `grep` 检查整个代码库里所有真正往 `raw_events` 表写数据的地方（`SessionManager.ts` 的 `storeRawEvent`、`beginInputRound`、`recordUserInputEvent` 三个方法，最终都调用 `RawEventStore.append()`），没有一处代码读取过 `CLAUDE_MEM_RAW_EVENT_STORE` 这个配置项的值——全部是无条件执行写入。

**触发条件与影响范围（本地核实后修正）**：远端审查报告最初描述的触发场景是"用户配置 `CLAUDE_MEM_RAW_EVENT_STORE=false` 后，原始事件仍然被保存"，暗示这是用户能通过正常操作触发的问题。但本地核实后发现：第 2 点提到的校验逻辑，已经在设置接口层面**明确拒绝**把这个值设成 `false`——也就是说，普通用户通过设置页面或调用设置接口，根本没有办法把这个值改成 `false`，自然也就不会"配置了却没生效"，因为这条路从一开始就走不通。

真正能触发这个问题的路径，只有绕开正常设置接口、直接编辑本地的 `settings.json` 配置文件，手动把这个字段的值改成非 `true` 的字符串——这不是产品设计上鼓励或支持的操作方式，普通用户日常使用不会走到这一步。所以这是一个**代码层面"校验和实现不一致"的问题**（配置项存在校验规则，但没有对应的执行逻辑），而不是一个用户能在正常使用中直接踩到的功能性缺陷。

**复现方法**（修正后的真实触发路径）：
1. 直接编辑本地 `~/.claude-mem/settings.json` 文件（绕开设置页面/接口），把 `CLAUDE_MEM_RAW_EVENT_STORE` 字段的值改成 `"false"` 或其他非 `"true"` 的值。
2. 重启 worker 服务，让新的配置文件生效。
3. 正常使用一次会话，产生工具调用、观察等内容。
4. 查询 SQLite 数据库 `raw_events` 表，会发现依然有新记录不断写入，配置文件里的"false"没有起到任何拦截作用。

**影响范围**：只有主动绕开正常设置渠道、手动编辑配置文件的用户才会撞到这个"改了没用"的现象；通过正常设置页面/接口使用产品的用户完全不会遇到这个问题（因为接口层面就不允许设成 false）。

## 3. 根因分析

**分析方法**：代码走查（追踪配置项从定义到使用的完整链路）。

**分析过程**：

1. 用 `grep -rn "CLAUDE_MEM_RAW_EVENT_STORE" src/` 搜索整个源码目录，只找到 3 处提及：
   - `SettingsDefaultsManager.ts` 里的类型声明和默认值定义；
   - `SettingsRoutes.ts` 里把这个字段加入"允许查询/展示"的配置项列表；
   - `SettingsRoutes.ts` 里前面提到的那段校验逻辑。
2. 完全没有找到任何一处，在实际"写 `raw_events` 表"的代码路径里，去读取并判断这个配置项的值。
3. 对比同一批改动里其他"真正生效"的配置项（比如 `CLAUDE_MEM_RAW_EVENT_MAX_AGE_HOURS`、`CLAUDE_MEM_RAW_EVENT_MAX_COMPENSATION`，这两个在 `SessionManager.prepareActiveSessionRecovery` 方法里有实际被读取和使用），可以确认这次改动里，配置项"声明+校验"和"消费使用"这两件事本身是分开做的，`CLAUDE_MEM_RAW_EVENT_STORE` 这一个恰好只完成了前一半、没有连上后一半。

**关键证据**：
- `src/shared/SettingsDefaultsManager.ts:203`（默认值定义）
- `src/services/worker/http/routes/SettingsRoutes.ts:139`（加入配置项列表）
- `src/services/worker/http/routes/SettingsRoutes.ts:276-278`（校验逻辑，拒绝非 true 值）
- `src/services/worker/SessionManager.ts` 的 `storeRawEvent`/`beginInputRound`/`recordUserInputEvent` 三个方法（均无条件写入，未读取该配置项）
- 对照组：`src/services/worker/SessionManager.ts` 的 `prepareActiveSessionRecovery` 方法，确实读取并使用了同批新增的另外两个配置项，说明"读取配置项来控制行为"这个模式在这批改动里是存在的，只是没有应用到这一个配置项上

**根本原因**：这个配置项从命名和校验逻辑上看，像是"预留了未来可能支持关闭原始事件归档"的设计意图（校验信息里"must remain true because raw events are always retained"这句话本身也暗示了"目前设计上就是强制保留，未来也许会开放"），但目前的实现里，"是否写入"这个判断压根没有做——不是"开关坏了"，而是"开关从来没有被真正接到电路上"，属于配置声明和实际使用逻辑之间的实现缺口，不是运行时的逻辑错误。

**未解开的疑点**：
- 这个配置项未来是否真的计划开放给用户关闭（即产品真实意图是"以后可能做成可关闭的"），还是纯粹的历史遗留/过度设计（一开始规划了但后来改变主意，忘了清理）？这属于产品设计意图判断，本档案不猜测结论，留给解决方案阶段和用户一起确认方向。

## 4. 解决方案

**【结论先说】**：这个问题本质是"有个装饰性的配置项，不影响任何用户能触碰到的实际行为"，紧迫度不高，但建议尽快理清楚——要么把这个配置项和校验逻辑一起删掉（如果确定不打算支持关闭），要么把它真正接入写入逻辑（如果确实想支持关闭）。不建议就这么放着，容易在未来造成"我明明改了配置怎么没生效"的困惑（哪怕目前只有手动改文件才会撞到）。

**推荐方案：先向用户确认产品意图，再二选一**
- **选项 A（如果确定不需要"可关闭"这个能力）**：删除 `CLAUDE_MEM_RAW_EVENT_STORE` 这个配置项的定义、默认值和校验逻辑，避免留下一个名不副实的配置项。
  - 好处：代码更干净，不会有人被这个"看起来能关、实际关不掉"的配置项迷惑。
  - 代价与风险：几乎没有，纯删除操作，不影响任何现有功能（因为它本来就没被使用）。
- **选项 B（如果确实需要支持"关闭原始事件归档"这个能力）**：在 `SessionManager.ts` 的 `storeRawEvent`/`beginInputRound`/`recordUserInputEvent` 三个方法里，统一加一层判断：读取 `CLAUDE_MEM_RAW_EVENT_STORE` 配置，值不是 `'true'` 时跳过对 `RawEventStore.append()` 的调用。同时需要考虑：这次改动引入的"输入轮次切片"功能（`InputRoundStore`）本身依赖 `raw_events` 表里的记录做切片，如果关掉归档，轮次切片这个新特性可能需要跟着降级为"不做轮次切片，退回旧的按消息类型直接处理"的逻辑，这部分需要专门设计。
  - 好处：让配置项名副其实，用户真的能通过设置控制这个行为，满足"隐私/磁盘占用敏感用户想少存点数据"的诉求。
  - 代价与风险：改动范围比选项 A 大得多，需要同时解决"关闭归档后，依赖归档数据的轮次切片功能该怎么办"这个连带设计问题，不是简单加个 if 判断就能完事的。

**最优解与理由**：本档案不替用户拍板选 A 还是选 B——这是一个产品设计意图判断（要不要支持关闭原始事件归档），不是纯技术问题。但建议无论选哪个，都要**尽快决定**，不要让这个"声明了但没接线"的配置项继续留在代码里，容易在后续开发中被其他人误以为"这个开关已经好使了"而在别处依赖它。

**实施步骤**（选定方向后）：
1. 若选 A：删除 `SettingsDefaultsManager.ts` 里的定义、`SettingsRoutes.ts` 里的列表项和校验逻辑三处代码。
2. 若选 B：在三个写入方法前统一加判断，并设计"关闭归档后轮次切片功能如何降级"的具体方案（这部分需要单独评估，工作量可能不小，必要时可以再拆成一个独立的标准问题）。

**回退办法**：选 A 是纯删除，如需回退直接恢复这几行代码即可；选 B 涉及新增判断逻辑和可能的降级设计，回退方式视具体实现而定，建议实施时保持改动可以整体撤销（比如控制在同一个提交里）。

## 5. 关联影响

- **横向影响**：如果选 B（真正接入开关），会牵扯到这次改动新引入的"输入轮次切片"功能（`InputRoundStore`/`round_slices`），因为这个新功能本身依赖 `raw_events` 里的记录作为切片的数据来源，需要一并设计"归档关闭时轮次切片怎么办"，影响面比表面上看起来大。
- **纵向影响**：不涉及数据库表结构变更（无论选 A 还是选 B，都不需要改 `raw_events` 表的结构）。
- **文档与注释**：如果最终选 A（删除），需要确认面向用户的设置说明文档（如果有的话）里没有提前介绍过这个配置项，避免文档和代码不一致。
- **同类隐患**：建议顺带排查项目里是否还有其他"声明了配置项和校验规则，但实际代码没有读取使用"的类似情况，属于举一反三的排查项，不在本档案范围内展开。

## 7. 附加说明

本问题最初由远端（ChatGPT）审查报告作为 P1-3 条目提出，原描述场景是"用户关闭该配置后原始事件仍被保存"。本地核实 `SettingsRoutes.ts` 的校验逻辑后发现，该场景实际上无法通过正常设置渠道触发（校验直接拒绝非 true 值），因此把触发路径修正为"仅手动编辑配置文件才能触发"，并据此把严重度从 P1 降级为 P2。这一处修正已经和远端确认并达成一致（远端在收到本地核实结果后同意降级）。是否要把这个配置项做成真正可用的开关（选 B），还是直接删除（选 A），最终由用户拍板选择了 A。

**生产方/执行方**：本次改动首次采用 GCP 协作模式（远端确认对仓库有读写权限后直接实施并推送），而非此前三份档案使用的 MIX 模式（远端出方案文本、本地落地）。远端直接在仓库里完成删除并提交（commit `4f0cb509`），本地拉取后独立核验类型检查与回归测试。核验中发现远端的"排查结论"遗漏了 README.md 里一处公开文档引用，已要求远端补充删除（commit `0b08dd7e`）。

**过程事故记录**：远端在补充 README 改动时，第一次提交（`b0511681`）因为 git 基准算错，把仓库几乎全部文件（1358 个中的 1357 个）误删并直接推送到了 `main` 分支——`main` 曾短暂指向这个内容几乎为空的提交。远端自行发现后未使用 force-push 改写历史，而是追加了一次修复提交（`0b08dd7e`）把完整仓库树恢复回来。本地已核实当前 `main` HEAD 状态完整正确（文件数、类型检查、回归测试与改动前基线全部比对一致），但这次事故说明 GCP 模式下"远端直接推送公共分支"存在真实风险——如果事故窗口期间有其他自动化（CI、部署）拉取了 main，会拿到被清空的仓库。已就此事故向用户汇报，用户决定后续问题继续使用 GCP 协作，但要求远端改为推送到非 `main` 的独立分支，由本地核验后再合并，不再直接写主分支。
