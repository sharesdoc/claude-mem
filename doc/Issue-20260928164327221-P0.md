# 省钱用的"自动切换便宜模型"功能，这次改动之后已经完全不起作用了

## 1. 问题状态

- 问题等级：P0
- 完成状态：待处理
- 测试状态：未测试
- 概要描述（大白话）：系统本来有个功能，看到待处理的都是些简单的读文件、搜文件之类的操作时，会自动换成更便宜的模型去处理，省钱又省时间。这次改动把"去查有哪些待处理任务"这一步，改成调用了一个系统里压根不存在的方法名，导致查询结果永远是空的，这个自动省钱功能从此彻底失效，而且新加的测试用假数据掩盖了这个问题，让人以为它还在正常工作。

- 分析依据 / 来源：本次代码审查（审查范围 commit `dd51045a3a5864e902eb4f79506dc84759a40670`(不含) 到 `5138a6b742d18e42479d8c2ff9fd18290d83ece0`(含)，7 个提交、51 个文件）。本地独立发现，并与远端（ChatGPT）审查报告的 P1-2 条目互相印证（远端定级 P1，本地核实证据链完整后建议升级为 P0，因为这是"原本能工作的功能被改坏"的回归，不是新功能没做完）。
- 所属计划项：无（项目无 M-系统开发计划体系）

## 2. 问题描述

**正常应该怎样**：系统有个叫"分级路由"（tier routing）的机制：一次用户对话结束、进入下一轮时，系统会先看看上一轮攒下来的待处理任务都是什么类型——如果全是"读文件、搜索、列目录"这种简单只读操作，就用便宜的小模型去处理这些任务；如果里面有"总结归纳"这类任务，就用专门配置的总结模型；都不是的话就用默认模型。这个决策逻辑写在 `applyTierRouting()` 方法里。

**实际怎样**：这个方法在查询"上一轮都有哪些待处理任务"时，调用了一个叫 `peekPendingTypesForRound` 的方法——但这个方法名在生产环境实际使用的对象上根本不存在，调用结果永远是"未定义"，导致查询条件永远判假，待处理任务列表永远被当成"空的"，于是永远不会切换到便宜模型或总结模型，分级路由功能形同虚设。

**问题背景**：这次改动前，`applyTierRouting()` 用的是 `peekPendingTypes()`（不带 "ForRound" 后缀），这个方法是真实存在且能正常工作的。这次改动为了配合新加的"按轮次切片处理"功能，把调用换成了 `peekPendingTypesForRound()`，但这个新方法名只在最底层的 `PendingMessageStore` 类里加了，中间那一层"队列引擎"（无论是 SQLite 版还是 BullMQ 版）都没有把这个方法转发/暴露出来。`applyTierRouting()` 实际拿到手的对象是队列引擎，不是最底层的 store，所以调用的方法根本不存在。

**复现方法**：
1. 配置好分级路由相关的环境变量：`CLAUDE_MEM_TIER_ROUTING_ENABLED=true`、`CLAUDE_MEM_TIER_SIMPLE_MODEL=一个便宜模型的名字`、`CLAUDE_MEM_TIER_SUMMARY_MODEL=一个总结模型的名字`。
2. 让一次对话的上一轮全是简单只读工具调用（比如只用了 Read、Grep）。
3. 触发下一轮生成器启动，观察实际使用的模型——预期应该是配置的便宜模型，实际会发现用的还是普通默认模型，说明分级路由没生效。

**复现路径**：
- `src/services/worker/http/routes/SessionRoutes.ts` 第 655-703 行左右（`applyTierRouting` 方法定义）
- 具体出错的调用在第 664-675 行
- 判断依据的正式接口定义在 `src/server/queue/ObservationQueueEngine.ts` 第 59 行（`ObservationQueueInspection` 接口）

**影响范围**：所有开启了分级路由功能（`CLAUDE_MEM_TIER_ROUTING_ENABLED=true`，这是出厂默认值）且配置了简单模型/总结模型的用户，每一次对话的每一轮都会受影响——这不是偶发问题，是每次都必然失效，影响面是全体启用该功能的用户，后果是本该省钱省时间的机制完全不起作用（花了更贵模型的钱、也可能因为模型选择不当影响处理效果），且用户完全无感知（不会报错、只是安安静静地不生效），没有任何绕过办法，只能等代码修复——定为 P0。

## 3. 根因分析

**分析方法**：变更差分法（对比改动前后代码）+ 接口/实现比对（检查方法名在类型定义、各个实现类、调用点之间是否一致）。

**分析过程**：

1. 先确认改动前的旧代码：`git diff` 显示，旧版 `applyTierRouting()` 调用的是 `pendingStore.peekPendingTypes(session.sessionDbId)`，这个方法在正式接口 `ObservationQueueInspection` 里是存在的（`peekPendingTypes` 方法，不是本次讨论的 `peekPendingTypesForRound`），说明旧逻辑是能跑通的。
2. 查看新代码（第 664-675 行）：
   ```ts
   const pendingStore = this.sessionManager.getPendingMessageStore() as unknown as {
     peekPendingTypesForRound?: (sessionDbId: number, promptNumber: number) => Promise<...>;
   };
   const targetPrompt = session.lastPromptNumber - 1;
   const pending = targetPrompt > 0 && pendingStore.peekPendingTypesForRound
     ? await pendingStore.peekPendingTypesForRound(session.sessionDbId, targetPrompt)
     : [];
   ```
   这里用了 `as unknown as {...}` 做了一次不安全的类型断言，强行给 `pendingStore` 加上了一个 TypeScript 编译器不会检查真假的"承诺"方法 `peekPendingTypesForRound`。
3. 查真实的类型定义 `src/server/queue/ObservationQueueEngine.ts` 第 59 行，`ObservationQueueInspection` 接口只声明了 `peekPendingTypes` 和 `peekPendingTypesForPrompt` 两个方法，没有 `peekPendingTypesForRound`。
4. 查两个具体实现类：`SqliteObservationQueueEngine`（同文件）和 `BullMqObservationQueueEngine`（`src/server/queue/BullMqObservationQueueEngine.ts`），都只实现了 `peekPendingTypesForPrompt`，都没有 `peekPendingTypesForRound`。
5. 确认 `this.sessionManager.getPendingMessageStore()` 返回的到底是什么类型：查 `SessionManager.ts` 第 640 行，`getPendingMessageStore(): InspectableObservationQueueEngine`，返回类型正是上面第 3、4 步查过的队列引擎接口，不带 `peekPendingTypesForRound`。
6. 反过来查"真正拥有" `peekPendingTypesForRound` 方法的地方：`src/services/sqlite/PendingMessageStore.ts` 第 309 行确实有这个方法，但这是"最底层的 SQLite 存储类"，队列引擎是包了一层的上层封装，`applyTierRouting()` 拿到的是队列引擎，够不着最底层的这个方法——这一层"转发"从来没有被接上。
7. 查配套新增测试 `tests/services/worker/http/routes/session-routes-tier-routing.test.ts` 第 98-128 行第二个测试用例，发现它自己手写了一个假的 `pendingStore` 对象，里面**手动添加了** `peekPendingTypesForRound` 这个方法（第 109 行），这个假对象比生产环境里真实存在的任何一个类都"更强"（多了一个真实类没有的方法），所以测试能通过，但测试验证的是一个不存在的世界。

**关键证据**：
- `src/services/worker/http/routes/SessionRoutes.ts:664-675`（出错调用）
- `src/server/queue/ObservationQueueEngine.ts:59`（正式接口定义，不含该方法）
- `src/server/queue/ObservationQueueEngine.ts` 中 `SqliteObservationQueueEngine` 实现（只有 `peekPendingTypesForPrompt`）
- `src/server/queue/BullMqObservationQueueEngine.ts`（同样只有 `peekPendingTypesForPrompt`）
- `src/services/worker/SessionManager.ts:640`（`getPendingMessageStore()` 返回类型声明）
- `src/services/sqlite/PendingMessageStore.ts:309`（`peekPendingTypesForRound` 唯一存在的地方，但够不着）
- `tests/services/worker/http/routes/session-routes-tier-routing.test.ts:109`（测试 mock 了不存在的方法）

**根本原因**：这次改动新增了"按轮次切片"的数据模型和底层查询方法（`peekPendingTypesForRound`），但只加在了最底层的存储类上，没有同步更新中间的队列引擎接口和两个实现类，把这个新方法"传导"上去；而 `SessionRoutes.ts` 里为了让代码能编译通过，用了 `as unknown as {...}` 这种绕开类型检查的写法，把一个实际不存在的方法当成"可能存在"的可选方法来调用——这种写法本身就是一个危险信号：正常情况下如果直接用真实类型（不做这个断言），TypeScript 编译器会在编译阶段就报错"这个方法不存在"，这个错误是被断言硬生生"关掉"了检查警报后才潜入生产环境的。配套测试又用了一个和生产环境不一致的假对象，进一步掩盖了这个问题，让代码审查和测试都没能拦下来。

**未解开的疑点**：
- 为什么会选择用 `as unknown as {...}` 断言而不是直接扩展正式接口？没有找到直接证据说明这是有意为之还是疏忽，本档案不做主观揣测，只陈述"断言绕开了类型检查"这一客观事实。

## 4. 解决方案

**【结论先说】**：把 `peekPendingTypesForRound` 正式补进队列引擎的接口定义，让两个实现类都真正实现它，然后把 `SessionRoutes.ts` 里那处不安全的类型断言删掉、改成直接用正式接口调用——这样以后如果再有类似的方法名对不上的问题，编译阶段就会直接报错，不会再悄悄溜进生产环境。改动集中在 3 个文件，风险可控，建议尽快修复。

**推荐方案：把方法补齐到正式接口，去掉不安全断言**
- **怎么做**：
  1. 在 `src/server/queue/ObservationQueueEngine.ts` 的 `ObservationQueueInspection` 接口里新增 `peekPendingTypesForRound(sessionDbId, promptNumber)` 方法签名。
  2. `SqliteObservationQueueEngine` 里新增该方法的实现，内部直接转调 `PendingMessageStore.peekPendingTypesForRound()`（底层方法本来就是好的，只是没接上来）。
  3. `BullMqObservationQueueEngine` 里新增该方法的实现，按 `roundSlice` 不为空且 `prompt_number` 匹配目标轮次的条件过滤已有任务列表（可以参考它现有的 `peekPendingTypesForPrompt` 实现思路）。
  4. `SessionRoutes.ts` 第 664-666 行删掉 `as unknown as {...}` 那段断言，直接把 `pendingStore` 当作正式的 `InspectableObservationQueueEngine` 类型使用，第 671-673 行的三元表达式里的"方法是否存在"判断也可以去掉（正式接口保证方法一定存在）。
- **好处**：从源头堵住"方法名对不上却能编译通过"的漏洞，两种队列引擎（SQLite/BullMQ）都能享受到分级路由功能，行为一致。
- **代价与风险**：需要给 `BullMqObservationQueueEngine` 补一个新实现（这部分之前完全没有），工作量比单纯改 `SessionRoutes.ts` 大一些；需要新写测试，且必须用真实的两个引擎类而不是手写假对象来验证。
- **适用前提**：无特殊前提，是根治方案。

**备选方案：临时先改回旧方法名**
- **怎么做**：`SessionRoutes.ts` 里先改回调用 `peekPendingTypes()`（旧的、确实存在的方法），先让分级路由重新"能用"，但这样就拿不到"只看上一轮"这个更精确的范围（会退回到"看整个会话所有待处理任务"的旧口径），按轮次切片的精细化效果暂时享受不到。
- **好处**：改动极小、能最快恢复"分级路由至少能生效"这个底线。
- **代价与风险**：损失了这次改动想要达成的"只看上一轮"精确路由的设计目标，属于权宜之计，后续还是要走推荐方案把 `peekPendingTypesForRound` 真正接上。
- **适用前提**：如果时间紧张需要先止血，可以先用这个方案顶上，但要在问题里明确记录"这是临时方案，根治方案仍待实施"。

**最优解与理由**：推荐**把方法补齐到正式接口**这个根治方案。这次问题的教训就是"用类型断言绕开检查"引入了一个隐蔽的方法名不匹配问题，如果只是换回旧方法名，虽然能让功能重新工作，但没有解决"新功能（按轮次路由）从来没有真正接通"这个更大的问题，也没有堵住类似问题以后重演的可能性。

**实施步骤**：
1. `ObservationQueueEngine.ts` 补接口方法签名。
2. `SqliteObservationQueueEngine` 实现转调底层 store。
3. `BullMqObservationQueueEngine` 补实现。
4. `SessionRoutes.ts` 去掉类型断言，改用正式接口。
5. 新增/改写测试：分别用真实的 `SqliteObservationQueueEngine` 和 `BullMqObservationQueueEngine` 实例（不是手写假对象）驱动 `applyTierRouting()`，验证分级路由在两种队列引擎下都能正确判断。

**回退办法**：如果补接口的改动引发新问题，可以先回退到"备选方案"（改回调用 `peekPendingTypes()`），保证功能至少不是彻底失效状态，再排查根治方案里的具体问题。

## 5. 关联影响

- **横向影响**：`ObservationQueueInspection` 接口目前被 `SessionRoutes.ts` 一处消费；补充新方法不会影响其他调用方，但需要确认没有其他地方也依赖"这个接口只有两个方法"这个假设（比如做接口 mock 的测试代码，新增方法后如果测试用严格模式的假对象可能需要同步补齐，属于常规联动，不是设计冲突）。
- **纵向影响**：
  - `BullMqObservationQueueEngine` 目前完全没有"按轮次查询"的实现，需要新写查询逻辑（基于内存里的任务列表过滤，不涉及数据库结构变更）。
  - 不涉及任何数据库表结构或迁移改动，纯代码逻辑修复。
  - 需要同步更新 `tests/services/worker/http/routes/session-routes-tier-routing.test.ts` 里那个手写假对象的测试用例，把它替换或补充成基于真实引擎类的集成测试，防止"测试和生产环境脱节"再次发生。
- **文档与注释**：无需更新面向用户的文档；建议在补充实现时，给 `peekPendingTypesForRound` 加清晰的接口注释，说明它和 `peekPendingTypesForPrompt` 的区别（"只看某个轮次里被切片标记过的任务"vs"看某个 prompt 编号下的全部任务"），避免未来又出现语义混淆。
- **同类隐患**：项目里如果还有其他地方用了 `as unknown as {...}` 这种绕过类型检查的写法调用队列引擎的方法，建议一并排查，这属于举一反三的排查项，不在本档案范围内展开。

## 6. 回归测试

**验证目标**：证明分级路由功能在真实的 SQLite 和 BullMQ 两种队列引擎下都能正确按轮次识别待处理任务类型，并据此切换到对应的模型。

**测试方法**：单元测试（分别针对两种真实引擎类）+ 集成测试（贯穿 `applyTierRouting()` 到 `ClaudeProvider.startSession()` 的真实调用链）。

**测试步骤**：
1. 用真实的 `SqliteObservationQueueEngine` 实例（连接一个测试用的内存/临时 SQLite 数据库），构造一个"上一轮全是简单只读工具"的场景，调用 `applyTierRouting()`，断言 `session.modelOverride` 被设置成了配置的简单模型名。
2. 同样场景下用真实的 `BullMqObservationQueueEngine` 实例（配合测试用 Redis 或 mock 的队列客户端）重复验证。
3. 构造"上一轮包含总结任务"的场景，验证 `modelOverride` 被设置为总结模型。
4. 构造"上一轮任务类型混杂（既非全简单、也非总结）"的场景，验证 `modelOverride` 保持未设置（用默认模型）。
5. 保留原有测试里"零配置场景下不会误用默认值短路模型判空校验"的用例（这个是之前 rev 审查已经发现并修复过的问题，回归测试要确保没有被这次修复带坏）。

**通过判据**：上述所有场景在两种引擎下的断言都符合预期即为通过；只要有一种引擎或一种场景下分级路由没有按预期切换模型，即为不通过。
