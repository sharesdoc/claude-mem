本次审查针对 `Task-20260927091425627-P2.md` 这份任务档案驱动的一次代码修改——把 Claude/Qwen/DeepSeek/OpenRouter/Gemini 五家 AI provider 的"模型名未显式配置时静默回落内置默认型号"这一行为改成"次级厂商判不可用自动跳过、Claude 报错阻塞"，覆盖 worker 主路径与 server-beta 独立路径共 10 个源文件与配套测试。该任务已经过 fix skill 三轮实现与独立验证，功能层面（provider 自身的模型解析、可用性判断、报错触发）已确认正确；本次审查在此基础上做独立第三方复核，重点是三轮验证都局限在"provider 单元本身"，未沿真实调用链走到底，因此本次审查的核心价值在于把审查视角拉高到"整条会话初始化调用链"，检验任务的核心目标是否真的在生产环境的主干路径上成立。结论是：单元层面的实现基本扎实（两位审查员分别只挑出边界条件层面的判空/一致性问题），但存在一个此前三轮验证完全没有覆盖到的调用链缺口——`SessionRoutes.ts` 里的 tier routing 机制会在最常见的"简单工具观察"场景下用出厂默认值 `'haiku'` 短路掉本任务新加的判空校验，使"未显式配置就不能用默认模型"这一核心诉求在多数真实运行场景下并未真正生效，这一发现直接影响任务档案里"零配置路径会被破坏"这一断言的准确性,需要用户对处理方向做裁决。

## 4. 必须处理（P0）

**R-001 [blocking] Tier routing 的 `'haiku'` 出厂默认值，让"零配置直接跑 Claude"这条路径在最常见场景下完全绕过本任务新加的模型名校验**

- 位置：`src/services/worker/http/routes/SessionRoutes.ts:600-633`（`applyTierRouting()`）+ `src/shared/SettingsDefaultsManager.ts:200-202`（`CLAUDE_MEM_TIER_ROUTING_ENABLED: 'true'`、`CLAUDE_MEM_TIER_SIMPLE_MODEL: 'haiku'`，本任务清零默认值的清单未纳入这两个字段）+ `src/services/worker/ClaudeProvider.ts:181-188`（本任务新加的判空校验）
- 事实依据：`applyTierRouting()` 是每次会话初始化/摘要生成都会走的标准前置步骤（非边缘路径）。当 pending 消息全部是 `Read`/`Glob`/`Grep`/`LS`/`ListMcpResourcesTool` 这类简单只读工具产生的观察记录时（插件日常使用中最常见的一类场景），`simpleModel = settings.CLAUDE_MEM_TIER_SIMPLE_MODEL` 取到出厂默认 `'haiku'`（非空真值）→ `session.modelOverride = 'haiku'`；`ClaudeProvider.startSession()` 第 181 行 `const modelId = session.modelOverride || this.getModelId();` 因此短路，本任务新加的空模型名校验（186 行）根本不会被求值。两位审查员均已用真实调用链追踪与复现验证，非推测。
- 推理说明：只有当 pending 消息包含 `summarize` 类型（`CLAUDE_MEM_TIER_SUMMARY_MODEL` 出厂默认是空串，不会覆盖 `modelOverride`）或者"既非全简单也无 summarize"的混合类型时，`modelOverride` 才会保持 `undefined`，让 `getModelId()` 的空串真正生效并抛错——也就是说本任务的核心诉求只在这两类场景下才真正生效，在最常见的"全简单工具"场景下并不生效。这个 gap 无法被本次新增的 3 个测试文件捕捉，因为它们都是直接构造 `session` 对象或 mock `loadFromFile`，从未经过 `applyTierRouting()` 的真实路径。
- 影响范围：任务档案 §5「关联影响」的绝对化断言（"一个从未设置过任何 CLAUDE_MEM_* 环境变量或 settings.json 的全新安装……将无法在零配置状态下生成新的观察记录/摘要"）与实际行为不符,对"简单工具观察"这一大类场景不成立。更根本地，`CLAUDE_MEM_TIER_SIMPLE_MODEL='haiku'` 正是用户在任务来源里明确要消灭的"未显式配置却偷偷用内置默认型号继续跑"这一类行为，只是换了一个配置项名字（tier routing 而非主 model 字段），三轮独立验证均未发现,因为验证范围从未覆盖真实调用链。
- 修复建议：需要用户裁决——(a) 若认定 tier routing 的模型选择也应遵守本任务"未显式配置不回落默认值"的新规则,则 `CLAUDE_MEM_TIER_SIMPLE_MODEL` 出厂值也应清零（`applyTierRouting()` 的 `if (simpleModel)` 判断逻辑本身已经正确处理"为空则不赋值"，只是出厂默认值非空导致条件恒真,不需要改这部分逻辑本身）；(b) 若认定 tier routing 是独立于本任务的机制（类比任务档案第 7 章对 `report-provider.ts` 的裁决先例——"不在本任务原始需求范围内,不应被本任务附带改变行为"）,则至少需要修正任务档案 §5 的绝对化措辞,明确"零配置路径破坏"只对非 tier-routing-simple 场景成立。
- 需补测试：一条贯穿 `applyTierRouting()` 真实逻辑的场景测试——零配置 + pending 消息全为 `SIMPLE_TOOLS` 类型时，验证 `ClaudeProvider.startSession()` 的实际行为（抛错或不抛错，取决于上述裁决）。
- 置信度：高（两位审查员各自独立复现）
- 处理建议：需用户裁决处理方式，合并前应至少修正档案描述或升级为已知限制并明确记录

## 5. 建议处理（P1）

**R-002 [important] ClaudeProvider 的模型名判空校验漏 `.trim()`，纯空格值绕过新增报错门槛**

- 位置：`src/services/worker/ClaudeProvider.ts:181,186,523`
- 事实依据：`getModelId()`（523 行）`return settings.CLAUDE_MEM_MODEL;` 未 `.trim()`；`startSession()` 的 `if (!modelId) throw ...` 对纯空格字符串（真值）不触发。已用复现测试验证：mock `CLAUDE_MEM_MODEL: '   '`，guard 未触发。
- 推理说明：Claude 是选型链条终点、无上游 `isXAvailable()` 守卫，这个判断是唯一防线；5 个 provider 里 Gemini/Qwen/DeepSeek 的模型解析均统一用 `(x ?? '').trim()`，此处是唯一漏做 trim 的一处。
- 影响范围：用户配置带尾随空格（常见操作失误）会静默绕过本任务"未配置就报错阻塞"的核心目标。
- 修复建议：`getModelId()` 返回值补 `.trim()`，或判断处改为 `if (!modelId?.trim())`。
- 需补测试：`CLAUDE_MEM_MODEL` 为纯空格时应抛错的用例。
- 置信度：高（已复现）

**R-003 [important] Qwen/DeepSeek 的 `isXAvailable()` 新校验插在函数最前，`loadFromFile()` 异常时直接短路 `false`，绕过原有"env 优先"及"文件不可读回退凭据存储"的容错设计**

- 位置：`src/services/worker/QwenProvider.ts:429-441`、`src/services/worker/DeepSeekProvider.ts:427-437`
- 事实依据：改动前，`isXAvailable()` 第一条语句就是 `process.env.CLAUDE_MEM_XXX_API_KEY` 检查，不依赖 `loadFromFile` 是否成功。本次新插入的模型名校验把"读文件"步骤提到最前面,且其 `catch` 分支直接 `return false`,不再有"回退到凭据存储"的机会。
- 推理说明：`settings.json` 存在但内容损坏时（手动编辑出错、磁盘写入中断），即使用户已通过 env 变量配好 API key，也会被新插入的模型名校验短路成不可用——这是本任务新引入的、与"模型名未配置"这个本任务核心问题无关的边界回归。
- 影响范围：仅影响 `settings.json` 存在但解析失败这一边界场景；正常场景不受影响。
- 修复建议：把模型名校验移到 env-优先检查之后，或让模型名校验的 `catch` 分支不直接 `return false`，改为"视为模型未配置但继续走后续 apiKey 判断逻辑"。
- 需补测试：`loadFromFile` 抛异常且 env 已配置 API key 时，核实 `isXAvailable()` 的返回值是否符合预期。
- 置信度：高

## 6. 可后续优化（P2 / P3）

- **P2** `src/services/worker/OpenRouterProvider.ts:536` 的模型解析未 `.trim()`，与 `isOpenRouterAvailable()`（:549）的判断口径不一致，纯空格值可绕过 `startSession()`（:155）的"双重保险"校验——正常选型主链路不受影响（先被 `isOpenRouterAvailable()` 拦下），仅在该守卫被绕过的路径下显现。建议改为 `(settings.CLAUDE_MEM_OPENROUTER_MODEL ?? '').trim()`，与其余三家保持一致。
- **P3** `QwenProvider.ts:433/444`、`DeepSeekProvider.ts:430/440` 的 `isXAvailable()` 对同一 settings 文件重复 `loadFromFile`（模型名校验与 apiKey 校验各读一次），可合并为一次调用复用结果，纯性能 nit。
- **P3** `GeminiProvider.ts:527-541` "配置了但不在白名单里的无效值→warn+回落默认模型"这一分支的既有行为按任务档案裁决原样保留（不在本任务范围内），但新增测试只覆盖了"未配置"与"合法值"两种情况，缺一条专门锁定"无效值→warn+回落且不抛错"的回归测试，属覆盖盲区，建议后续补上以防未来维护误改。
