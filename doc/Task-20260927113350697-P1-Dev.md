# 按用户每次输入分轮，异步生成完整的观察记录

## 1. 任务状态

- 任务等级：P1
- 完成状态：已实现待测试
- 测试状态：已完成定向验证，待独立测试闭环
- 概要描述（大白话）：把一次用户输入到下一次用户输入之间发生的所有原始事件作为一轮，等这一轮结束后再异步生成观察记录；用户结束会话时也要补上最后一轮，同时不阻塞 Claude Code 的正常工作。
- 来源与依据：用户连续讨论结论；由 tsk 根据当前对话建档
- 所属计划项：无
- 关联需求：无

## 2. 需求描述

当前每次工具调用都可能触发一次观察内容生成，导致模型调用频率过高，而且单次观察缺少同一轮处理过程中的完整上下文。本任务把观察记录的触发单位从“单个工具调用”调整为“用户输入开启的一轮处理”。

用户明确要求：

1. 原始事件记录与 Claude Code 自身执行完全分开。原始事件必须持续记录，观察记录和摘要信息通过异步流程生成，不能让 Claude Code 停下来等待。
2. 用户输入定义为“用户输入事件”，一次用户输入开启一轮新的处理范围。
3. 用户输入事件之后，记录本轮的所有内部执行事件，包括工具调用和其他内部调用，不限制具体调用类型。
4. 用户再次输入时，先关闭并异步处理上一轮，再开始记录新的用户输入事件及其内部执行事件。
5. 用户直接结束会话时，关闭并异步处理最后一轮尚未生成观察记录的原始事件。
6. 第一次用户输入不需要处理上一轮；只有存在上一轮未处理内容时，新的用户输入才触发上一轮处理。
7. 同一轮原始事件过大时，按指定大小切分为多个异步处理切片；切片只描述处理范围，不改变原始事件记录。

本任务不要求 Claude Code 等待观察或摘要结果，也不要求删除原始事件。模型不可用时，异步处理可以延期，但原始事件不能丢失。

事件编号统一采用以下概念（经核实现有代码，前两项直接复用现成字段，详见 §3）：

- 用户输入事件编号：复用现有的 `prompt_number` 字段（整数自增计数器），用来标识一轮处理，不使用毫秒时间戳。
- 内部执行事件编号：复用永久 `raw_events` 表现成的自增主键 `id`，按 `prompt_number` 过滤、按 `id` 排序即为一轮内的顺序。
- 内部处理切片编号：仅当本轮内容超过指定大小时产生，用来标识本轮被切分后的处理批次——这是本任务唯一需要新建编号的地方。

## 3. 需求分析

一次用户输入到下一次用户输入之间，通常包含用户目标、工具调用、工具返回、文件修改、测试结果和最终响应。这些内容作为整体交给观察生成模型，比按单个工具调用生成更能反映完整处理过程。

处理边界必须在用户输入事件到达时固定：

- 当前轮事件持续写入原始事件存储。
- 新用户输入到达时，前一轮被标记为已关闭，并生成不可变的处理范围。
- 新用户输入及其后续内部事件进入下一轮，不能混入上一轮。
- 会话结束时，当前未关闭轮次被关闭并提交异步处理。
- 异步处理只读取已经关闭的轮次；新轮次继续写入不会影响正在处理的切片。

现有永久原始事件表和待处理队列可以作为基础。需要增加“轮次关闭”和“异步处理切片”的元数据，不能依靠扫描当前不断增长的事件集合来推断边界。

经核实现有代码（`SessionStore.ts`、`schema.sql`、`PendingMessageStore.ts`），下面两种编号并非要从零新建，而是复用现成字段，这一点必须在实现前定下来，避免重复建设：

- **用户输入事件编号直接复用现有的 `prompt_number` 字段**。`user_prompts`/`pending_messages`/`observations`/`session_summaries` 四张表都已经带这一列并配好索引，且它本身是整数自增计数器，不是毫秒时间戳，天然不存在"同一毫秒内重复编号"这个问题——不需要另外设计唯一性保证。
- **内部执行事件编号直接复用永久 `raw_events` 表现成的自增主键 `id`**。`pending_messages` 是临时处理队列，成功后可以清理，不能作为永久事件编号。按 `prompt_number` 过滤后再按 `raw_events.id` 排序，就是同一轮内的事件顺序，不需要另建一套新的递增计数器。
- 真正需要新增的是：①一个能表达"这一轮是否已关闭、可以提交异步处理"的状态位——现状里完全没有这个概念；②切片的起止原始事件编号与状态；③把现在"逐条 `for await` 单条处理"的消费循环改成"按已关闭轮次批量取出多条原始事件、拼成一次或多次生成请求"。
- 轮次状态建议落在一张新的轻量表（例如 `input_rounds`，主键为 `content_session_id + prompt_number`），不建议在 `pending_messages` 逐行加"轮次已关闭"标记——轮次是否关闭是"这个 `(会话, 用户输入编号)` 整体"的属性，不是每条内部事件各自的属性，用独立表能避免每来一条新事件就要去更新一批旧行的状态。
- 同一会话的异步切片需要保持顺序，并且重复投递不能重复生成观察记录——这一条 enqueue 层已有 `content_session_id + tool_use_id` 唯一索引兜底"同一条内部事件不会被重复记录"，但"同一个切片任务被重复投递到异步队列"这件事仍需要切片表自身的幂等键（轮次编号 + 切片编号）来保证，两者不是同一层面的问题，不能只依赖前者。
- Sub Agent 事件必须纳入同一套原始事件记录机制，至少保存 `agent_id`、`agent_type`；如果事件带有父 Agent 或父事件关系，也要保存对应标识，确保可以还原主 Agent 与 Sub Agent 的调用关系。没有通过 Hook 或事件入口上报的 Sub Agent 内部行为，不得假定为已记录。

## 4. 设计方案

【最优解】采用“实时原始事件流、用户输入关闭轮次、异步切片处理”的方案。

### 事件层级

```text
会话
└── 用户输入事件 U-<prompt_number>（复用现有 prompt_number 字段，非新建编号）
    ├── 内部执行事件（复用 raw_events 现有自增 id，按 prompt_number 过滤后排序即得序号）
    ├── 内部执行事件
    ├── 内部执行事件
    └── 内部处理切片 U-S1：事件 id 区间 [start, end]（新概念，需新建）
```

建议在原始事件及处理元数据中保存（标注哪些是复用现有字段、哪些是真正新增）：

- 会话标识、用户输入事件编号——**复用现有 `content_session_id`/`prompt_number`**，无需改动；
- 内部执行事件编号——**复用 `raw_events` 现有自增 `id`**，无需新增列；
- 事件类型和原始内容——统一先写入永久 `raw_events`，再按需要写入 `pending_messages` 作为异步处理索引；`pending_messages` 处理成功后可以清理，不承担永久保存职责。原始事件类型需要覆盖用户输入、工具调用、其他内部操作和 Sub Agent 事件，并保存 `agent_id`、`agent_type` 及可用的父关系标识；
- 处理切片编号、切片起始/结束 raw event id、轮次或切片状态——**新增**，落在一张新的轻量表（如 `input_rounds`：主键 `content_session_id + prompt_number`，列含 `status`（open/closed/processing/completed/failed）、`closed_at`；子表 `round_slices`：轮次引用、切片序号、起止 `raw_events.id`、切片状态），不在 `pending_messages` 逐行加标记。

### 处理流程

1. 用户第一次输入时，若不存在待关闭的上一轮，直接在 `input_rounds` 插入一行 `open` 状态记录（主键为 `content_session_id + prompt_number`），不提交上一轮处理。
2. 每个内部调用事件先写入 `raw_events`，天然携带所属 `prompt_number` 与自增 `id`，不触发模型调用；只有需要生成观察记录的事件范围才另外写入 `pending_messages`。
3. 用户再次输入时，原子地把上一轮 `input_rounds` 行状态改为 `closed`，按其 `prompt_number` 取出全部 `raw_events` 行（按 `id` 排序），按大小创建一个或多个 `round_slices`，然后投递异步观察生成任务。
4. 新用户输入插入新的 `input_rounds` 行（新 `prompt_number`），后续事件按现有逻辑归入新的 `prompt_number`，不需要额外归属判断。
5. 会话结束时关闭最后一个 `open` 状态的 `input_rounds` 行，并按同样规则生成 `round_slices`。
6. 异步 Worker 按切片读取永久原始事件，生成观察记录；观察生成失败时保留切片和原始事件，按既有受限补偿规则重试，临时 `pending_messages` 行是否清理不影响原始事件。
7. 一轮只产生一个切片时，该切片的观察记录直接作为本轮结果；一轮产生多个切片时，按切片编号顺序拼接各切片的观察记录，形成轮次结果，不额外调用模型。
8. 摘要生成如果依赖观察记录，应以第 7 步产出的轮次结果为输入，并保持同一轮次和切片顺序。
9. **与现有 tier routing 联动**：`applyTierRouting()`（`SessionRoutes.ts`）现状是"读取当前会话全部未处理 pending，据其工具类型决定模型档位"，与轮次概念无关。本任务实施后，tier 判断的范围要收窄到"当前正在提交处理的这一个已关闭轮次/切片"，而不是整个会话的全部未处理消息——否则一个会话里前面几轮是复杂操作、当前这轮全是简单读操作，仍会被前面几轮的复杂度错误影响判档；这个联动点必须在实现时同步改，不能保持现状不动。

### 大批量切片规则

切片只在轮次关闭后计算。优先按事件顺序连续切分，并记录每个切片的事件编号范围。大小限制可以按字符数、序列化字节数或估算 token 数定义，但必须使用稳定的配置值，不能因为新事件到达而改变已经关闭的切片。

切片失败或模型暂不可用时，只改变异步处理状态，不回写或删除原始事件。处理任务必须通过“轮次编号 + 切片编号”幂等，避免重试生成重复观察记录。

备选方案是继续按工具调用直接触发观察生成，再由后续摘要合并。这种方案改动较小，但无法解决高频模型调用和单个观察上下文不完整的问题，不采用。

## 5. 关联影响

- 原始事件接收链路：现有的用户输入编号（`prompt_number`）与永久内部执行事件编号（`raw_events.id`）不需要改动，只需要新增"轮次"这一级的生命周期记录（新表 `input_rounds`/`round_slices`）。
- 数据库：新增轮次表与切片表，并建立唯一约束（`content_session_id + prompt_number`）与查询索引；`pending_messages` 保持临时处理队列语义，永久事件只保存在 `raw_events`。
- 异步队列：需要增加"关闭轮次后投递切片"的任务类型、幂等键、重试和顺序控制；多切片轮次只需在模型处理完成后按顺序拼接结果，不新增汇总模型调用。
- 观察生成：输入从单个工具事件改为已关闭轮次的一个或多个切片；多个切片的观察结果按顺序组成轮次结果。
- 摘要生成：需要识别观察切片的顺序和完成状态，读取的是按顺序组成的轮次结果，不能读取仍在写入的开放轮次。
- **tier routing 联动**：`applyTierRouting()` 的判断范围需要从"会话全部未处理 pending"收窄为"本次提交处理的轮次/切片"，这是本任务必须同步修改的现有机制，不属于范围外。
- 会话结束流程：必须保证最后一个开放轮次先关闭，再提交异步任务。
- 模型不可用处理：继续保留原始事件；只延期异步观察和摘要任务，不阻塞 Claude Code。
- 性能：模型调用次数会减少，但单次请求平均输入量会增加，需要控制切片大小和队列并发。
- 数据规模：原始事件永久保留，观察切片元数据也会增加数据库容量；本任务不新增原始事件清理策略。
- 测试与文档：需要同步更新事件模型、异步处理流程、配置说明和相关测试。

## 6. 测试方案

验收标准：

1. 第一次用户输入只创建轮次，不触发上一轮观察生成。
2. 同一轮内多个工具调用和内部事件都被记录，并且内部执行事件编号连续递增。
3. 第二次用户输入到达后，上一轮被关闭并异步投递；第二轮事件不会进入第一轮。
4. 会话结束时，最后一轮被关闭并异步投递，即使没有下一次用户输入也不会遗漏。
5. Claude Code 继续执行时，异步观察和摘要任务不会阻塞用户输入、工具调用或内部事件记录。
6. 轮次内容未超过大小限制时生成一个切片；超过限制时生成多个连续切片，切片边界不重叠、不遗漏。
7. 新事件在异步处理期间继续写入时，不会进入已经关闭的轮次或正在处理的切片。
8. 异步任务重复投递或失败重试时，不会重复生成同一个轮次切片的观察记录。
9. 模型不可用时，原始事件和已关闭切片仍然保留，模型恢复后可以按既定顺序补偿。
10. 会话重启、异常退出和正常退出后，已关闭轮次与最后开放轮次的状态均可恢复。
11. 一轮只产生 1 个切片时，该切片的观察记录直接作为本轮结果，不触发额外模型调用。
12. 一轮产生多个切片时，全部切片的观察记录生成完毕后，按切片编号顺序拼接为轮次结果，不触发额外模型调用。
13. `applyTierRouting()` 对某一轮/切片的模型档位判断，只依据该轮/切片自身的内部事件类型，不受会话中其它轮次（尤其更早、已处理完的轮次）的内容影响。
14. 处理成功的 `pending_messages` 行可以被物理删除，但对应的 `raw_events` 行必须始终保留，处理前后可以在永久原始事件表中查到同一条事件记录。

建议测试层级：

- 单元测试：轮次关闭状态机、切片边界、大小限制、幂等键、多切片按顺序拼接（含"恰好 1 个切片"这一边界）。
- 数据库集成测试：事件写入、轮次状态、切片范围、唯一约束、重启恢复、`pending_messages` 清理后 `raw_events` 仍保留的验证。
- 异步队列测试：投递、顺序、重试、模型不可用、重复任务、"全部切片完成后按顺序形成轮次结果"的时序控制。
- 端到端测试：用户输入 → 多个内部事件 → 下一次用户输入 → 会话结束的完整流程；另需一条覆盖"内容超过切片阈值 → 多切片 → 顺序拼接"的完整链路。
- 联动测试：同一会话前一轮为复杂操作、当前轮全部是简单工具时，`applyTierRouting()` 对当前轮的判档不受前一轮影响。
- 回归测试：现有原始事件永久保存、活跃会话补偿、观察生成和摘要生成流程。

## 7. 附加说明

- “内部处理切片编号”是处理批次标识，不是新的原始事件类型。
- 用户输入事件编号与内部执行事件编号分别复用现有的 `prompt_number` 字段与 `raw_events` 自增 `id`，不新建编号体系；本任务真正新增的是"轮次"这一级的生命周期状态（新表）与切片逻辑，实现时应避免重复建设已经存在的编号机制。
- 用户输入事件和内部执行事件的原始内容必须先持久化，再异步投递处理任务。
- 本任务只定义按用户输入分轮和异步切片处理的机制，不直接改变模型提示词的具体文字内容；提示词如何组织整轮事件属于实现阶段的技术细节。多切片结果只按顺序拼接，不额外调用模型。

本次实现已覆盖：永久 `raw_events`、用户输入分轮、关闭轮次切片、开放切片保护、切片顺序消费、多切片结果按顺序拼接且不额外调用模型、旧普通队列消息兼容、会话结束恢复 flush、Sub Agent 原始事件归属、SQLite/BullMQ 队列路径和幂等迁移。

实现验证：`bunx tsc --noEmit` 通过；核心定向测试 76 通过、0 失败、1 跳过；迁移相关测试 19 通过；全量服务测试仍有既有 schema repair、provider fixture 和 observation labeling 环境问题，真实 Redis/BullMQ 端到端测试未执行。因此本档案进入“已实现待测试”，不提前标记为测试关闭。
